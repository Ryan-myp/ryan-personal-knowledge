# 广告 Agent 知识质量标准

本标准用于判断知识库是否达到可供广告 Agent 稳定使用的生产级水平。文档数量不是评分主体；每个结论都必须能被定位、解释、验证和安全地转化为下一步动作。

## 评分模型

| 维度 | 权重 | 9.5 分门槛 |
|---|---:|---|
| 覆盖完整性 | 20% | 四平台均覆盖对象、创建、测量、报表、优化、诊断和行业场景 |
| 事实与证据 | 25% | 官方来源可追溯，版本/适用边界明确，事实与经验分开 |
| 实战可执行 | 25% | 有前置条件、字段/资源、步骤、失败恢复、回退和验收 |
| 检索与回答 | 20% | 关键问题 Top-3 命中率、MRR 和跨平台误召回持续达标 |
| 治理与安全 | 10% | 版本、发布、废弃、脱敏、权限边界和变更日志完整 |

没有检索评测和来源复核时，最高只能评为 7 分；只有文档数量增长而没有案例和证据时，不能加分。

## Canonical 文档要求

每个平台至少维护一篇 Canonical Runbook，且必须包含：

- 资源层级和父子关系，以及创建/读取/更新/暂停/归档边界。
- 业务输入到平台字段族的映射，动态枚举以当前 Tool schema 为准。
- 创建前 preflight、dry-run、幂等、提交、readback 和上线验收。
- 交付、事件、报表和业务结果的状态机。
- 至少三类异常的证据顺序、恢复动作和回退条件。
- 一个完整案例，明确事实、假设、证据、动作和不确定性。
- 官方来源、适用版本、政策变化风险和当前能力边界。

## 内容分层

文档正文使用以下标记习惯表达结论：

| 类型 | 写法 | 允许的结论 |
|---|---|---|
| 官方事实 | 明确资源、接口、字段或政策来源 | 可作为平台事实引用 |
| 当前能力 | 指向 Registry/Tool Source/Tool schema | 只代表本项目当前实现 |
| 运营经验 | 写明样本、窗口、前提和失效条件 | 只能作为建议或假设 |
| 推断 | 明确证据和不确定性 | 不能伪装成平台保证 |
| 待确认 | 列出缺失数据和查询计划 | 只能输出排查，不得自动写入 |

固定阈值、行业 benchmark、转化最低量和“保证提升”类表述必须有来源、样本范围和适用条件，否则降级为待验证假设。

## 发布门禁

发布前必须检查：

1. frontmatter 完整，ID 唯一，版本为语义化版本，状态合法。
2. 正文非空，至少包含一个工作流/决策表/诊断路径和来源。
3. 不包含 token、secret、原始 PII、MCP、Provider client 或可执行脚本。
4. 新增平台字段已经标明版本和动态能力边界，不覆盖当前 Tool schema。
5. 检索案例集新增至少一个命中样例和一个边界样例。
6. 更新 `index.md`、`log.md` 和受影响的来源/版本说明。

## 检索评测

评测问题按平台、目标、对象、动作、异常、测量和行业分层。每个 case 记录 query、期望文档、允许的相关文档、不可出现的跨平台误召回和人工判定说明。

- `Hit@3` 衡量 Top-3 是否包含期望知识。
- `MRR` 衡量首个相关结果的位置。
- `Cross-platform leakage` 衡量用户明确指定平台时是否被其他平台文档覆盖。
- `Answer faithfulness` 由人工或受控模型复核回答是否只使用检索到的证据。

当前默认使用 SQLite FTS5/BM25；没有 Embedding 时应优先优化标题、别名、字段词、章节粒度、平台过滤和评测案例，不用虚假的语义准确率替代验证。

## 维护节奏

平台 API、政策和字段变化时创建新语义版本，记录来源、影响文档、迁移、回滚和复核人。每轮发布后运行知识质量脚本、检索 smoke test、相关测试和 `git diff --check`；发现 bad case 时先保留原问题和错误结果，再修正文档或检索策略。
