# 模板对话与创建工作区可靠性修复

## 已确认的缺口

- 模板目录结果后附带澄清选项时，通用 Harness 优先恢复澄清来源，跳过已选目录项的详情 Tool。
- 模板必填输入不完整时直接暴露创建工具，补参没有稳定进入只读模板草稿入口。
- 分轮编辑模板时只合并本轮覆盖值，先前表单中的名称、日期、预算可能丢失。
- 前端把“补充字段，但不要提交”误判为退出创建流程。
- 资源查询未匹配时仍触发级联校验；结构重绘重新自动查询，可能反复消耗渠道 QPS。
- 级联选项在 API 和 UI 中形态不同，产生无效重绘，且可能保留已经不合法的选项。
- 历史草稿打开后只恢复显示，不恢复后续编辑所需的模板上下文。
- 参数解析失败被统一隐藏，明明表单参数齐全，用户却只得到笼统的补参提示。
- 上一轮对 `scope_required=False` 的处理过宽，账户可选的 Tool 也错误丢弃了显式账户。

## 实现边界

通用 Harness 仅根据已注册 Tool 的 namespace、resource、action 和结果 ID 元数据，
把唯一的目录选项绑定到只读详情 Tool。结果 ID 仍是候选参数，不是执行授权。

广告应用通过已有模板服务读取当前身份可见的模板。未齐全的模板输入只暴露现有的
`get_creation_template` Tool；该 Tool 返回更新后的 `ad_creation_form`。
表单齐全后才进入蓝图创建 Tool 和既有签名确认流程。

模板读取 Tool 的执行上下文仅增加数据字段 `creation_request`，保存本轮模板 ID 和
表单参数，用于分轮合并。其他 Tool 不接收这份上下文。不新增渠道 Router 或 Provider 执行入口。

已知参数校验错误使用 `ToolArgumentValidationError`，经过脱敏和长度限制后展示。
未知异常仍不返回内部错误原文。创建表单保留原字段，并通过 `validation_error` 显示拦截原因。

自动资源校验按会话、账户、字段、所选值和声明的依赖组合去重，包括未匹配的结果。
账户、依赖或值变化会允许新查询；手动查询始终可重试。此缓存不是授权，
服务端仍会校验 selection token、账户范围、权限、确认、幂等和审计。

## 验证与证据边界

- `make ad-agent-check` 完整通过：2813 项 Python 测试、编译、Tool 契约快照、
  Provider 能力审计及知识库检查。
- 前端静态回归 124 项通过。重点覆盖的目录选择、模板服务及账户范围三个模块，
  行覆盖率合计 93%；这不是整个服务的覆盖率。
- 本地测试覆盖三渠道模板选择、分轮合并、用户/租户隔离、非法覆盖值、完整表单提交边界。
- 浏览器通过真实服务和 LLM 完成 TikTok 模板查询、选择、文字补参，确认工作区有预填字段。
- 浏览器重放历史草稿，确认恢复可编辑上下文而不恢复旧写入批准。
- 重绘回归中，额外资源查询数和额外级联校验数均为 0。
- 浏览器展示测试默认替身化 `/parameter-options/resolve`，不反复调用渠道。
  没有发送 `confirmed=true`，不作为 Campaign、Ad Group 或 Ad 创建成功证据。
- `verify_template_dialog.js` 是显式运行的 UI smoke test，不加入默认离线单测，
  需要已安装的 Chrome、Playwright 以及正在运行的本地服务。
- 仓库全局 qguard 仍未通过，不能将局部测试通过表述为整个仓库达到质量目标。

## 部署与恢复

无数据库迁移，不更改默认 dry-run、测试账户白名单或 live 工具批准清单。
后端更新后需重启服务；静态资源版本已更新，避免旧 JS 缓存。
回滚代码和静态资源即可，模板、知识库和聊天记录不应清空或替换。
服务本次仍由 tmux 托管，本机重启后的自动恢复尚未配置，属于明确剩余运维项。
沿用现有 Run 事件和审计字段，没有新增观察性服务依赖。
