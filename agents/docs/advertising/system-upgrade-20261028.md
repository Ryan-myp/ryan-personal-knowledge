# 广告 Agent 全面评估与本轮升级

日期：2026-10-28。沿用单 Agent、Run Kernel、Turn Pipeline、Skill/Tool contracts，
保留既有工作区修改和业务数据；没有新增渠道 Router、第二套 Runtime、数据库后端或外部服务。
本轮广告渠道执行使用离线替身，真实模型使用部署中配置的 Agnes；不更新渠道 live 验收状态。

## 整体判断

系统已经具备可扩展的单 Agent 底座、三渠道 Tool 与模板、知识检索、托管 Skill、
任务和治理链路。主要弱点是跨层契约和证据传递：Tool 选对后，参数未必正确；
多轮会话可能看不到最新结果；Skill 与引用竞争上下文；静态知识中的能力边界可能过期。
注册了 321 个 Tool 不等于所有真实业务路径稳定通过，也不能用本地测试数量代替对话准确率。

| 维度 | 当前有依据的能力 | 薄弱点与本轮处理 |
| --- | --- | --- |
| 架构 | 通用 Harness 与广告组合、Provider、持久化边界已建立 | 输出裁剪代码混在执行协调器中，应用历史预览另用字符串截断；本轮抽出通用 `tool_output.py`，两个入口复用同一 JSON 预算逻辑 |
| 意图识别 | 依据 Registry 的 action/resource/alias/traits 限定可见工具，再由模型调用 | “不要改成列表”仍可能触发列表选择；改为复用通用否定动作识别，中英文回归覆盖，不增加渠道或失败句专用分支 |
| 多轮上下文 | 有最近对话、用户约束、来源记录和有界历史召回 | 历史结果按旧到新拼接后截断；同名 Tool 更新不改变顺序。现在最新结果优先、重查移动到末尾，保留完整 JSON 与显式裁剪标记 |
| Skill 与知识 | 当前知识与 Skill 有版本和来源，引用按相关性选择 | 大 Skill 挤占预算、frontmatter 消耗指导预算、通用引用挤掉明确作用域引用。现在主指导优先并为辅助指导留份额，移除重复元数据，优先匹配有效 `reference_scope` |
| 广告查询 | 原有账户、Campaign 与下层级查询和报表契约继续使用 | 补充 Meta Campaign 当前状态筛选、规范日期枚举、结果集合声明和关联 Skill；避免成功调用但查询口径不对 |
| 稳定性 | 租约、取消、确认、幂等、熔断和超时仍由原链路控制 | 小输出预算连裁剪标记本身都可能超限；现在检查完整 JSON 大小并安全降级，原始结果仍由既有持久化和输出契约保存 |
| 性能 | Registry/客户端复用、Skill 上下文缓存和有界并发已存在 | 去掉同一 Skill 的重复评分，减少历史结果处理中无用的旧记录；本轮性能数据只证明局部路径，模型耗时仍占主要部分 |
| 评测 | 已有固定知识查询、对话回归、权限与 Provider 契约测试 | 新增同一次成功调用的参数断言，使用指纹比较；报告保存 Run 状态、执行状态和有界参数证据，避免只凭 Tool 名称算通过 |
| 权限 | 可信 principal、白名单、live/确认/幂等等门禁 | 本轮没有放宽权限、将记忆变成授权或向 Skill 开放 Provider 执行 |

## 实现与验收对应

| 需求 | 所属边界 | 验收证据 |
| --- | --- | --- |
| 主辅 Skill 均可进入上下文，关键引用不被元数据挤掉 | Harness Skill catalog、metadata、reference selection | 长短 Skill、always-on、来源隔离、frontmatter、作用域与原有广告引用回归 |
| 最新结果在连续追问中可见，不能把半截 JSON 当完整证据 | 广告 SessionContext/RuntimeContext + 通用输出裁剪 | 同名 Tool 重查、最新窗口、零/负窗口、凭证脱敏、Unicode/转义、极小预算与不修改原结果 |
| 否定列表操作不覆盖报表任务 | 通用 ToolSelector | 自定义 alpha namespace 的中英文否定筛选测试；实际 Meta 多轮模型案例 |
| 报表筛选与日期条件传到底层 | Meta Tool schema → 固定 Handler → Client | 封闭枚举、重复状态拒绝、ID 与状态 AND 合并到同一 Insights 查询（保留分页）、无效日期在网络前失败 |
| 参数错误不能蒙混过关 | 平台声明式评测 + 托管 Engine 观察器 | 正确 Tool/错误参数、不同调用拼凑参数、失败调用、缺证据、敏感字段和超限拒绝 |

## Meta 报表契约

`meta_get_campaign_report` 升级为 `2.2.0`：

- 保留已有可选 `account_id`、Campaign ID、日期、分页字段，新增 `effective_status`。
  当前支持 `ACTIVE`、`PAUSED`、`DELETED`、`ARCHIVED`，不自动添加默认状态过滤。
- ID 与状态条件合并为一次 Insights 查询的 AND 过滤，不额外读取账户或 Campaign 列表；
  保留原有的有界分页，不能解释成任意数据量都只产生一个 HTTP 请求。
- `effective_status` 是对象当前有效状态；报表日期仅限定指标时间，不能解释成历史状态快照。
- `date_preset` 使用 Meta 官方 Business SDK 的 `AdsInsights.DatePreset` 规范枚举。
  同时保留原契约的 `LAST_7_DAYS`、`LAST_14_DAYS`、`LAST_30_DAYS` 三个别名。
  Client 保留原有日期别名/大小写规范化；未传日期仍交由 Client 处理默认值。
  未支持的预设在发送前失败，离线 Handler 也不再伪装成功。
- `report_context` 标明状态条件及是否执行。离线数据仍明确标记 `simulated`、
  `offline_no_client`、`filters_executed: false`，不能作为平台数据或 API 连通证明。
- 显式关联 `meta-marketing-api-expert` 和 `account-diagnostics`，通过元数据加载 SOP。
  Meta Skill 升级到 `2.2.0`；账户诊断 Skill 升级到 `1.5.0`，修正“Campaign 报表不暴露
  time_increment”的过期描述，继续保留 breakdown 和归因窗口的真实限制。

Provider 的 `filtering` 参数参考官方 SDK 的
[Campaign Insights 参数定义](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/campaign.py)，
日期枚举核对了官方
[AdsInsights 定义](https://github.com/facebook/facebook-python-business-sdk/blob/main/facebook_business/adobjects/adsinsights.py)。
Meta 文档站部分页面在本环境不可访问；状态过滤的具体 HTTP payload 已做离线契约验证，
本轮没有用真实账户确认上游接受情况，因此不标记为 live 验证通过。

Python Client 的新增报表选项通过封闭 `MetaReportOptions` 声明，并拒绝未知选项。
既有关键字调用保持兼容；`time_increment` 应使用关键字传入，不再依赖旧的第八个位置参数。

## 评测证据如何解读

`tool_arguments` 是有界、不可执行的声明式断言，同一个成功调用必须同时满足所列参数。
调用前的已解析 Tool 参数由现有 `tool_execution_start` 事件采集；证据只保留参数指纹，
不复制用户查询原文或凭证。指纹比较不等于 HTTP 请求证明，Client 的规范化和参数发送另由
Provider payload 测试验证。大小写等规范化可能造成严格原始参数断言不通过，必须核对原因，
不能直接归类为业务失败，也不能把失败记录改写成通过。

本轮初测 3 例为 1 通过、2 失败，发现了两类问题：
报表追问被“不要改成列表”误导，以及参数检查揭示日期不一致。随后复测中，已能选对报表
并传入 PAUSED 条件；一次日期是 API 可规范化的 `YESTERDAY`，另一次日期指纹不匹配当前
已确认要求。原始记录保留，之后补充规范日期枚举，再对相同 Meta 案例定向复测。
通过批次和失败批次分别记录，不能拼成全系统一次全通过。

外部 `skill-up/run.sh` 已尝试执行，但宿主机没有 `skill-up` CLI，返回 127；
该外部入口不能算通过。内置 `skill_up_engine.py` 的契约回归和真实模型评测仍独立执行。

## 性能与验证

- 本地历史结果窗口合成样本：8 个结果、每个约 24000 字符、两条路径各采样 15 次。
  旧路径 P50 68.373 ms，新路径 P50 43.352 ms，约减少 36.6%；新窗口首先展示最新的
  `read_7`，旧窗口先展示 `read_0`。不包含模型、磁盘数据库或真实渠道耗时。
- 共享输出裁剪模块行覆盖率 92%，参数证据模块 85%，两者合计 88%；不是全系统覆盖率。
- 359 项 Provider payload、Meta 报表及相关预算/权限回归通过；原有跨业务 Skill 导出和
  广告引用断言继续保留，没有为通过测试删除关键业务要求。
- 日期枚举和否定语义修复后，Meta 直接查询、连续追问两例真实模型复测均通过，
  每例最后一轮只调用一次报表 Tool，日期与 PAUSED 参数断言通过。渠道使用离线替身，
  不是上游真实 API 验收；历史批次的失败记录保留。
- 增量静态检查：37 个变更 Python 源文件，基线 503 条、当前 500 条、新增 0 条。
  最近全仓扫描 758 个源文件、4990 条发现，完整静态门禁仍未通过。
- 最终 `make ad-agent-check` 退出码为 0：编译、能力审计、321 个 Tool 契约与快照校验、
  全量测试和知识检查通过；测试为 **3218 passed, 1 warning，308.58 秒**。
  85 篇知识页面校验无错误或警告。该测试警告来自 FastAPI/Starlette 的 httpx 弃用提示。
- 固定知识检索评测为 65 例，混合检索 Hit@3 为 1.0、Recall@3 为 0.887，
  7 个负例未误命中；这些数字仅代表该固定案例集，不代表开放问题的知识正确率。
- 验证汇总见 `../../evals/advertising/evidence/system-upgrade-verification-20261028.json`；
  模型初测、中间失败、诊断与定向复测、局部性能证据均分别保留在同一 evidence 目录。

## 仍然薄弱的地方

1. **语义泛化**：可见 Tool 集仍大量依赖词法相关性。此轮解决通用否定与指导衔接，
   不代表未知表达、跨主题和复杂组合任务已经稳定；需持续增加独立留出案例和用户反馈样本。
2. **同一长任务的证据压缩**：旧回合裁剪与最新结果窗口已经有界，但超大当前回合仍可能
   安全停止。尚未实现完整保留执行事实、关键 ID 和失败边界的通用渐进式摘要。
3. **模型延迟与容量**：真实模型请求仍常占大部分耗时；局部 25 ms 改善不等于端到端响应
   明显提速。SQLite 保持单进程部署，尚无本轮多用户生产容量证明，也没有引入 MySQL。
4. **渠道和创意闭环**：三渠道的真实能力以既有版本化 live 账本为准；本轮不重测广告创建、
   不扩大写权限，也不声明视频生成上游和自动优化闭环已经解决。
5. **知识专业性与维护**：修复了一处明确过期的 Skill 事实，尚未逐条核对全部知识来源。
   参数断言、固定检索命中和引用存在都不能替代广告结论、归因口径与统计方法的专业评审。
6. **工程债务**：核心模块仍偏大，全仓静态门禁有大量历史问题；本轮只要求增量无新增，
   不将其描述成全仓质量门禁通过。反思产出的规则仍须评测、版本化和可回滚，不能自动变成执行代码。

## 部署、恢复与回滚

没有数据库 schema 迁移、业务数据清理、端口或认证模式变更。异常输入由 schema/Provider
边界明确拒绝；裁剪仅影响有界模型视图，已执行结果仍走既有持久化与恢复链路。
发布时需要同步代码、Tool 快照和 Skill 包；现有托管 Skill 版本记录不被覆盖。
回滚应一起回滚上述版本化文件，不删除聊天、模板、蓝图或 Provider 账本。
继续使用现有阶段耗时、Run 事件和审计接口，没有新增必须部署的观察性服务。

本轮改动尚未提交、push 或重启服务。当前运行中的服务不能据此视为已经加载了本轮代码。
