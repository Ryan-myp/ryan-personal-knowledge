## 对话连续性与上下文预算

此前知识、Skill 和模板说明先占用上下文，位于后面的用户约束、已查到的资源信息可能
被截掉。现在应用渲染先给用户约束、资源观察和记忆分配空间，再加入知识和其余参考内容。
各来源有独立上限，分隔符也计入本段预算；空间不足时各连续性来源仍有预留份额。
这些内容都是 advisory，不能用于授予权限、确认写操作或替代实时校验。

当 Harness 已负责选择发布的 Skill 时，应用在总预算裁剪前就移除未使用的 Skill 副本。
这避免一份最后不会送给模型的重复文本，提前挤掉对话摘要或工具证据。
没有扩大上下文上限，也没有声称真实模型的意图准确率已经提高。

## 任务完成必须匹配当前租约

`TaskQueueStore.update_task` 新增可选关键字参数 `lease_owner`；广告存储和通用
SQLiteTaskQueueStore 同步实现。worker 的成功、失败、取消、超时和预执行失败路径均
传递自身 owner。写入同时核对当前状态和 owner，旧 worker 无法覆盖已恢复并被其他
worker 接管的同一 task_id。管理端不传该参数时保留原有生命周期操作契约。

handler 返回或抛错后，先停止 watchdog、收束 heartbeat，再判定终态。未结束的
heartbeat 表示归属仍不确定，任务进入 recovery_required。预执行 hook 后若已被接管，
不再调用 handler。取消期间返回未知副作用的结果也能正常进入 recovery_required，
避免停留在 cancelling。外部副作用不自动回滚，也不会因这些状态修复自动重放。

SQL 都留在 store 中。广告存储的任务完成语句改为固定列和绑定参数，保持原来的
result / workflow_id 保留语义，不拼接用户值。无 schema 迁移。

## 知识编辑和历史列表恢复

- 知识保存、发布以及后续列表刷新期间继续编辑，会保留新正文、手动版本号和 dirty
  状态，并保留已保存的 document_id；再次保存更新正确的文档，不退出编辑页。
- 只有提交快照与当前表单一致，才清除未保存状态。明确告知“提交内容已保存，新增编辑未保存”。
- 历史列表刷新改为收到有效响应后再替换。断网、HTTP 失败、无效 JSON 或错误分页结构
  保留原列表及游标；首次加载失败也能通过“重试刷新”恢复。
- 重试刷新从第一页读取，不把旧游标拼到新的列表上；较早响应继续受请求序号限制。
- 401 / 403 清除不可访问的列表并提示权限问题，不把权限变化当普通网络错误处理。
