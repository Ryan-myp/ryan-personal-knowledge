# 模型输入与流式输出边界加固

基于 `998d9f3`。这一轮处理通用 Harness 的资源边界与流式契约，
不增加 Runtime、业务路由、Provider Tool 或数据库迁移。

## 问题与实现

| 复现的问题 | 实现落点 | 验收边界 |
| --- | --- | --- |
| 历史、系统上下文和 Tool schema 分别有限，但合起来没有总输入限制 | `agent_harness/model_limits.py`、`Agent._model_inputs` | 所有消息及调用参数、Tool schema 合并计量；整回合裁剪 |
| 超大新消息可能先挤掉已有内存历史，再发现无法处理 | `Agent.run` 追加消息前检查 | 拒绝后保留原有历史，不调用模型 |
| SDK 添加文档正文与自动修复提示后可能再次超限 | `core/llm_client.py` 每次实际发送前检查 | 首次请求、附件正文和空回复修复分别测试 |
| 流式单片段超过 4096 字符会直接丢掉后面的文本 | `agent_harness/model_stream.py` | 切成多个事件，最终文本与所有片段拼接一致 |
| 只限单片段，不能阻止累计超大输出和连续空片段 | 同一流式组装边界与模型协调器 | 限制正文、Tool 参数、context updates 和片段数量 |
| 请求超时返回后，后台 iterator 后续产出的文字仍可能进入事件流 | 模型协调器的 invocation 局部停止信号与 deadline | 超时后释放阻塞，不能出现迟到 delta 或重建已清理的事件序列 |
| 流式 ToolCall 转换丢失 `argument_bindings` | `ModelExecutionCoordinator._stream_calls` | 保留依赖、字段绑定和源路径 |

没有修改意图识别规则，也没有为任何渠道或问句增加特殊分支。

## 配置与职责

`AgentApplication`、`Agent` 和平台 `GovernancePolicy` 提供一致的部署配置：

- `max_model_input_chars=256000`：模型准备阶段的消息和 Tool schema 总字符预算。
- `max_model_output_chars=128000`：返回正文、Tool calls 与 context updates 的字符预算。
- `max_stream_chunks=10000`：一次流式响应最多消费的片段数，空片段也计入。
- 新增配置必须为正整数，拒绝布尔、浮点、无穷和非正值。

原有模型、Tool 超时仍保持 500 秒默认值，不用缩短超时掩盖问题。
这些限制来自受信任的实例/平台配置，请求 context 不能抬高 Harness 的限制。
不同业务沿用同一个实现；新增 ModelAdapter 不需要修改业务 Router。

输入预算最初设置为 120000 字符时，19 项已有业务回归被拒绝。
核对到一个跨渠道暂停样本的完整准备输入为 191881 字符、32 个 Tool，
其中有大量非本次操作必要的创建类 schema。最终默认上限校准为 256000；
受影响的原有回归随后全部通过，没有修改这些回归的断言。
这个校准保留正常流程与完整契约，不代表输入规模已经足够精简。

## 保护与失败行为

系统规则、提供者上下文、Skill 指引、当前用户请求以及本轮 Tool 交互不被截断。
移除旧历史时以 user 开头的完整回合为单位；窗口开头已失去父调用的旧结果不再送入模型。
裁剪只改变本次模型视图，不修改完整持久化历史或原有内存记录。
必要输入本身超限时明确失败，不能通过裁剪 JSON、参数或权限说明来凑预算。

SDK 在附加文档文本后再次检查，并在每次自动修复发送前重新计量。
内嵌图片的二进制传输不算文字上下文；图片上传和传输大小由已有附件边界约束。
这不是所有模型统一的 token 估算，也不是模型端上下文窗口或整包字节数证明。
自定义适配器若在准备消息之外额外拼接上下文，仍需在自身发送边界执行同样约束。

输入/输出超限返回稳定错误码和可读说明，不自动重试本地资源拒绝，
不执行被拒绝模型回合里的 Tool calls。先前回合已经执行的结果仍保留在账本中，
不能把停止后续处理描述成外部操作已回滚。

流式消费在异常、主动取消、超时或超限后清理 iterator。清理发生在消费线程，
不会从另一线程强行关闭仍在执行的 generator。清理自身失败时不覆盖原始错误，
日志只记录异常类型。
上游调用若不响应取消，仍可能在有限槽位内继续阻塞；这里只保证停止本地后续处理，
不声称已经终止上游计费、网络任务或外部副作用。

## 验证口径

测试先复现丢字、迟到输出与缺失绑定，再实施修复。
定向检查 97 项通过；新增 `model_limits`、`model_stream` 两个模块的聚焦
语句覆盖率为 92%，不是全框架覆盖率。
最终 `make ad-agent-check` 通过：2734 项测试通过、1 项既有依赖弃用警告，
编译、Provider 契约审计、321 份 Tool 快照、知识审计与本地向量缓存检查均通过。
全仓 qguard 仍为 FAIL、0 分、4967 条发现，包含生成目录的重复副本；
没有关闭规则或删除构建产物来换取通过。
详细结果见 `agents/evals/advertising/evidence/model-resource-bounds-20261022.json`。

本地合成样本使用 321 条消息、32 个 Tool，重复裁剪 100 次：
输入从 140881 字符裁至 89561 字符，落在 90000 字符预算内；
保留 185 条消息，P50 为 2.836ms、P95 为 3.132ms。
这是独立窗口函数的合成开销，不是正常会话大小、生产吞吐或真实模型时延。

这一轮使用离线模型/Provider fixtures，不把离线回归描述成真实模型或真实广告 API 验证。
没有重启 8766 服务，没有修改凭证、SQLite 数据、蓝图、模板或知识库内容。
回滚只需回滚代码配置，不需要数据恢复。

## 仍需关注

部分请求的候选 Tool 契约仍然偏大。现在可以限制并测量总输入，但还不能声称已经
解决工具筛选精度、通用语义理解或真实模型稳定时延。
`model_start.input_chars` 和 `model_input_trimmed` 只记录大小与数量，
不保存 Prompt 或被移除的对话正文。

全仓 qguard 的既有结构性问题也不因本次新增边界而自动达标。
