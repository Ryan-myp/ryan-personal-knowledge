# 故障恢复与结果契约加固

本轮以 `8d4e291` 为基线，记录随后实现的故障恢复与结果契约改动。

## 复现与修复

| 缺口 | 归属 | 修复与验收 |
| --- | --- | --- |
| 写入结果未知且同时带 `is_error` 时，策略会先释放幂等预留 | 平台通用 Tool 策略 | 未知优先于失败；持久化隔离并审计为 unknown，保留原始 timeout 等诊断 |
| 过期 pending 可能来自执行中崩溃，不能证明未发生外部写入 | IdempotencyStore 与 SQL adapter | 未决预留不随 TTL 自动重放；重开数据库、人工核对与摘要绑定测试 |
| 熔断拒绝在策略预留后直接返回，跳过清理与审计 | Harness Tool 执行边界 | 已证明未进入执行器的拒绝经同一 after hook 清理，不把未执行描述成未知写入 |
| 多个预留的清理使用短路 any，首个失败会跳过后续清理 | 平台策略 finalizer | 尝试每个预留；任何失败返回恢复错误，仍写审计 |
| store 返回 `"false"` 会被 bool 转为执行许可；false finalizer 回执会被当成功 | 平台策略与端口契约 | reserve 必须返回 bool；完成/释放/隔离必须按端口确认，否则 fail closed |
| 持久化 adapter 将后端的 `"false"` 强转为 True；SQL 完成标记没有核对受影响行 | 广告 persistence adapter 与 SQL store | 不再强转后端答复；完成标记必须匹配一条未决记录，否则显式报错 |
| SDK 内部修复可重复获得完整 timeout，取消后仍可能追加请求 | 通用 LLM adapter 与模型协调器 | 共享绝对截止时间；准备与排队耗时计入；每次发送和接收后检查取消及租约 |
| Task 的成功字符串标签能覆盖失败与未知结果，字符串 false 被当真 | durable task outcome 边界 | 严格控制标记与终态，按强证据决定结果，保留正常 awaiting-input 分支 |
| `RunResult` 对象会被 JSON default=str 转成字符串，再被判作普通完成 | 同一任务边界 | 直接识别标准 RunResult，保留 failed / awaiting_input / recovery_required |
| 超大或不能保留的 Task 结果变成普通截断对象，被误判 succeeded | TaskExecutor 结果保留 | 明确 recovery_required 与安全原因，不把丢失的结果当成功 |
| 通用 TaskExecutor 默认原样持久化结果，可能留下敏感字段 | 后台任务持久化边界 | 默认使用通用持久化脱敏器；仍允许受信任应用注入自定义脱敏器 |

测试先复现上述问题，再实施修复。不增加渠道、特定问句或业务意图分支。
广告创建、查询、更新的 Provider Tool 契约没有改变。
旧回归用例由 `pending` 断言改为 `uncertain`，并将预留时间调至过期以验证重试仍被阻断；
原有第二次调用未触达 Provider 的断言保留。

## 安全与端口

`IdempotencyStore` 增加 `mark_uncertain` 与受信任核对用的 `resolve_uncertain`。
具体 SQL 仍在应用 persistence adapter 内；Harness/平台策略不写 SQL。
SQLite 与 MySQL 路径使用同样的请求摘要和状态条件，没有引入 SQLite 专属运行逻辑。

- `pending` 表示预留尚未安全决议。进程可能已开始调用，不能靠变旧就当作未执行。
- `uncertain` 明确隔离已报告的未知副作用。普通 release 与迟到的成功标记不能解除隔离。
- 已验证执行成功的记录进入 `executed`，按原配置保留有限去重窗口。
- 已证明没有调用执行器的拒绝正常释放，不需要人工解除。
- 核对操作必须匹配请求摘要，只能由受信任维护代码在确认外部结果和调用已静止后执行。
- 本轮没有新增用户解锁接口、LLM Tool 或可以自动作出外部核对结论的流程。
- 存储无法确认隔离/释放/完成时明确返回恢复错误，不静默假定成功。
- 完成标记的条件更新未匹配预留（含迟到结果遇到 `uncertain`）时抛错；
  保持原隔离记录，不将其悄悄改为 `executed`。

这不是外部 API 的 exactly-once 承诺。不同幂等键、Provider 自身语义、存储丢失、
操作者错误核对，以及不响应取消的上游仍有各自风险。
未使用持久 Store 的调试配置没有跨进程恢复保障；默认真实写入仍要求持久边界。

## Task 与模型语义

handler 正常返回只证明 handler 完成。返回标准 `RunResult` 才能保留单 Agent Run
的完整终态；业务结果和结构化子结果也参与判定，成功标签不能抹去它们。
协议错误、丢失结果和未知副作用要求核对；取消不能把未知副作用改写成普通 cancelled。
`awaiting_input` 的交互卡片不当作失败调用。
Task 结果与错误默认经通用持久化脱敏后写入队列存储；这不替代对外部 Provider
响应、日志和应用自定义脱敏器的逐层审计。

SDK 的修复、目录纠正和空回复重试属于同一次模型调用预算，不各自重置到 500 秒。
默认超时仍是 500 秒。取消和租约信号来自受信任 TurnRequest，不能由模型输出授权。
本地停止不代表能够强杀已经阻塞的网络调用，也不构成上游计费取消证明。

## 验证与部署

测试使用内存/临时数据库、离线模型与本地假执行器，没有真实广告 API 或付费模型调用。
MySQL 仅做离线 SQL 状态条件验证，不冒充真实 InnoDB 并发或服务器验证。
全量检查通过 2787 个测试，含 1 条 Starlette/httpx 弃用告警；Harness 与平台定向
测试通过 752 个。321 个 Tool 契约快照有效，Provider 契约审计、知识检索与
本地合成向量检查通过。九个测量模块的本轮变更可执行语句覆盖 189/209
（90.4%），不是全框架覆盖率。全仓 qguard 扫描仍失败，得分为 0
（740 个文件、4969 项发现，含已有构建副本）；没有为提高分数关闭规则或删除构建产物。
完整原始日志和统计记录在本轮 evidence 文件中。

没有更换数据库、修改表结构、清除记录，也没有修改业务蓝图、模板或知识库数据。
但这次是**行为变更**：未决预留不再随时间自动放行。
部署前应盘点已有未决预留，必要时核对；不能清表绕过，也不能把旧记录当成可安全重放。
仍有未决/隔离记录时，不应直接回滚到原来的 TTL 放行逻辑。需要先禁用真实写入、
完成受控核对或保留同等阻断规则，再决定回滚。

本轮没有重启 8766 服务，当前服务尚未加载本轮代码。

## 客观剩余

1. Tool 候选集合仍可能偏宽，模型常规请求并未因此自动变小。
2. 熔断恢复目前仍缺少单探针 half-open 和更细粒度的故障隔离，不能据此声称抗故障风暴已完善。
3. 隔离记录有安全的维护端口，但管理界面、核对证据审批与运维告警尚未形成完整闭环。
4. 本轮没有真实模型泛化测评或多机故障演练，也不宣称稳定的生产延迟与吞吐。
5. 全仓质量扫描仍需继续治理；不能拿本轮定向用例代替整体质量达标。
