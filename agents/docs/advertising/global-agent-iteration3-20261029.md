## 工具查找与实际加载一致

`RunToolDiscovery` 原来固定给发现入口预留一个位置，但展示阶段会放入全部发现入口。
注册多个发现能力时，会出现搜索已返回 loaded、下一次模型请求却放不下该工具的情况。
现在搜索与展示共享容量计算；容量不足明确返回 capacity_limit。

工具选择结果只用于确定名称和顺序，实际 schema 从当前注册目录取得。移除失效名称、
去重发现入口，避免旧选择器缓存中的定义覆盖当前 schema。显式 allowlist、发现时的
权限校验、加载窗口和搜索次数上限继续保留；最终执行仍走原权限和 live 门禁。
这些修复提高加载的一致性，不代表真实模型一定会正确选择或调用工具。

## 大结果仍能继续分页

模型输出裁剪优先保留 `next_cursor`、`next_page_token` / `nextPageToken`、`paging`
等分页信息，再压缩大列表。游标必须完整保留；若游标本身超预算，明确省略并记录
truncated_fields，不能把截短后的假游标当成下一次请求参数。

还修复了真实 Harness 链路中下一页 token 被通用脱敏误删的问题。只对明确的
`next_page_token` / `nextPageToken` 字符串或 null 保留，并继续扫描文本内的凭证赋值。
`page_token` 仍受保护，因为部分 Provider 用它表示页面访问凭证；access_token、
refresh_token、client_secret 等规则不变。嵌套对象、数组或相似名称不能借此跳过脱敏。

用假模型和两个本地分页响应验证了：大结果进入模型上下文后，仍能用原始游标继续
下一页；没有网络调用、真实凭证或渠道 QPS。未改变广告 Provider contract。

## 会话与 checkpoint 原子恢复

此前逐条读取、逐条覆盖内存状态；中途 metadata、timestamp 或 usage 损坏，会留下
半份恢复历史，并可能在下一轮继续使用。现在先解码和校验，完整成功后才替换消息和
usage；恢复失败抛出 TranscriptPersistenceError，沿用 recovery_required 返回路径。
原会话保持完整，修复存储后可重试，不静默当作新会话执行。

保存 checkpoint 明确返回 False 或抛错时，不再把它记成已保存，也不继续下一次模型/
工具批次。保留此前已完成的工具结果，并返回 recovery_required。兼容原存储接口中
成功返回 None 的实现，不自动重放已执行动作。

同时校验消息集合、metadata 对象和有限非负 timestamp，保留合法的零时间戳；拒绝
非有限 usage。当前可信 system 消息仍由服务提供，存储中的 system 消息不能替换它。
身份、租户和 session scope 仍先校验。

历史恢复改为全部解码后一次裁剪，继续按完整 user turn 保留历史，保持工具调用对。
本机 2,000 条消息、保留上限 200、7 次测量的中位值：原实现 56.556ms，改后 5.622ms；
两者保留 199 条消息。这是局部恢复基准，不能推导整体回复时延或线上准确率。
