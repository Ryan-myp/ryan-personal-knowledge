## 1. 分布式架构核心原理

### 1.1 CAP定理

```
CAP定理核心：

┌─────────────────────────────────────────────────────────────┐
│                                                             │
│   C (Consistency) - 一致性                                   │
│   ├── 所有节点在同一时刻看到相同数据                          │
│   ├── 强一致性：读操作返回最新写入的数据                       │
│   └── 最终一致性：允许短暂不一致，最终达到一致                  │
│                                                             │
│   A (Availability) - 可用性                                 │
│   ├── 每个请求都能获得非错误的响应                             │
│   ├── 不保证响应包含最新数据                                   │
│   └── 系统必须在合理时间内响应                                 │
│                                                             │
│   P (Partition Tolerance) - 分区容错性                       │
│   ├── 网络分区时系统仍能继续运行                               │
│   ├── 分布式系统必须保证P                                     │
│   └── 只能在C和A之间做权衡                                     │
│                                                             │
│   现实选择：                                                  │
│   ├── CP系统：ZooKeeper、HBase、Redis Cluster               │
│   ├── AP系统：Cassandra、DynamoDB、Eureka                   │
│   └── CA系统：单机数据库（无分区需求）                         │
│                                                             │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 BASE理论

```
BASE理论：

├── Basic Availability (基本可用)
│   └── 分布式系统在出现故障时，允许损失部分可用性
│
├── Soft State (软状态)
│   └── 允许系统存在中间状态，该中间状态不会影响系统整体可用性
│
└── Eventual Consistency (最终一致性)
    └── 所有数据副本经过一段时间后，最终达到一致状态
```

## 2. 一致性协议

### 2.1 2PC（两阶段提交）

```
2PC 协议流程：

Phase 1: 准备阶段
┌─────────┐    准备提交    ┌─────────┐
│  TC     │──────────────→│  TM1    │
│ (协调者)│               │ (事务1) │
└─────────┘               └─────────┘
     ↓                       ↓
     ↓   准备提交    ┌─────────┐   ↓
     └──────────────→│  TM2    │←──┘
                     │ (事务2) │
                     └─────────┘

Phase 2: 提交阶段
┌─────────┐    提交事务    ┌─────────┐
│  TC     │──────────────→│  TM1    │
└─────────┘               └─────────┘
     ↓                       ↓
     ↓   提交事务    ┌─────────┐   ↓
     └──────────────→│  TM2    │←──┘
                     └─────────┘

问题：
  - 同步阻塞：所有参与者阻塞直到决策
  - 单点故障：TC崩溃导致事务挂起
  - 脑裂：网络分区时决策不一致
```

### 2.2 3PC（三阶段提交）

```
3PC 改进：
  1. 可以超时提交
  2. 加入询问阶段，减少阻塞
  3. 加入可中断提交

缺点：网络开销大，仍不能完全避免脑裂
```

│       │ 注册        │ 注册        │ 注册                       │
│       └─────────────┴────────────┘                           │
│                        ↓                                    │
│              ┌─────────────────┐                            │
│              │  服务发现服务    │                            │

└─────────────────────────┼───────────────────────────────────┘
                          ↓
┌─────────────────────────────────────────────────────────────┐
│                        服务消费者                            │
│  ┌─────────┐  ┌─────────┐  ┌─────────┐                     │

### 3.2 负载均衡

```
负载均衡算法：

┌─────────────────────────────────────────────────────────────┐
│  1. 轮询 (Round Robin)                                     │
│     ┌───┐ ┌───┐ ┌───┐ ┌───┐                                │
│     │ A │→│ B │→│ C │→│ A │...                              │
│     └───┘ └───┘ └───┘ └───┘                                │
│                                                             │
│  2. 加权轮询 (Weighted Round Robin)                         │
│     权重：A=3, B=2, C=1                                     │
│     ┌───┐┌───┐┌───┐┌───┐┌───┐┌───┐                        │
│     │ A ││ A ││ A ││ B ││ B ││ C │...                       │
│     └───┘└───┘└───┘└───┘└───┘└───┘                        │
│                                                             │
│  3. 最少连接数 (Least Connections)                           │
│     选择当前连接数最少的服务器                                 │
│                                                             │
│  4. 一致性哈希 (Consistent Hashing)                          │
│     解决动态扩缩容时的数据迁移问题                             │
│     环形结构，节点分布均匀                                     │
│                                                             │
│  5. 随机算法 (Random)                                       │
│     简单但可能不均匀                                          │
│                                                             │
│  6. 源地址哈希 (Source Hashing)                              │
│     保证同一客户端请求同一服务器                               │
│     适合会话保持场景                                          │
└─────────────────────────────────────────────────────────────┘
```

## 4. 分布式事务

### 4.1 事务类型

```
分布式事务类型：

├── 强一致性事务
│   ├── 2PC：两阶段提交，强一致但性能差
│   ├── 3PC：三阶段提交，改进2PC
│   └── TCC：Try-Confirm-Cancel
│       ├── Try：预留资源
│       ├── Confirm：确认提交
│       └── Cancel：释放资源
│
└── 最终一致性事务
    ├── BASE事务：基本可用、软状态、最终一致
    ├── 可靠消息最终一致：
    │   ├── 本地事务 + 消息发送
    │   ├── 消息队列保证消息不丢失
    │   └── 消费者处理消息
    ├── Seata AT模式：
    │   ├── 无侵入，业务代码无改动
    │   ├── 全局锁 + 回滚日志
    │   └── 性能较好
    └── Seata TCC模式：
        ├── 需要实现三个接口
        ├── 性能好，但开发成本高
        └── 适合重要业务场景
```

### 4.2 Seata框架

```
Seata AT模式原理：

┌─────────────────────────────────────────────────────────────┐
│  TC (Transaction Coordinator) - 事务协调器                    │
│  ├── 管理全局事务状态                                         │
│  ├── 管理分支事务注册/汇报状态                                 │
│  └── 管理事务锁资源                                            │
│                                                             │
│  TM (Transaction Manager) - 事务管理器                        │
│  ├── 开启全局事务                                              │
│  ├── 注册全局事务                                              │
│  └── 提交/回滚全局事务                                         │
│                                                             │
│  RM (Resource Manager) - 资源管理器                           │
│  ├── 管理分支事务使用的资源                                     │
│  ├── 注册分支事务                                              │
│  └── 汇报分支事务状态                                          │
│                                                             │
│  执行流程：                                                   │
│  1. TM 通知 TC 开启全局事务                                    │
│  2. 各 RM 注册分支事务到 TC                                    │
│  3. 执行业务 SQL（自动生成 UNDO LOG）                         │
│  4. TM 通知 TC 提交/回滚全局事务                               │
│  5. TC 通知各 RM 提交/回滚分支事务                              │
│  6. RM 执行提交/回滚（利用 UNDO LOG）                         │
└─────────────────────────────────────────────────────────────┘
```

## 5. 分布式锁

### 5.1 实现方式

```
分布式锁实现方式：

┌─────────────────────────────────────────────────────────────┐
│  1. 基于数据库（唯一索引）                                      │
│     ├── 优点：简单可靠                                          │
│     ├── 缺点：性能差、非可重入                                  │
│     └── 实现：INSERT IGNORE 或 ON DUPLICATE KEY               │
│                                                             │
│  2. 基于 Redis（SETNX）                                      │
│     ├── 优点：高性能、支持分布式                                │
│     ├── 缺点：需要考虑 Redis 集群脑裂                           │
│     └── 实现：SET key value NX PX expire                     │
│                                                             │
│  3. 基于 ZooKeeper                                          │
│     ├── 优点：强一致性、支持临时节点                            │
│     ├── 缺点：性能较差、部署复杂                                │
│     └── 实现：创建临时顺序节点                                 │
│                                                             │
│  4. 基于 Redisson                                          │
│     ├── 封装了 Redis 分布式锁的全部特性                          │
│     ├── 支持可重入锁、看门狗机制                                │
│     └── 推荐生产环境使用                                        │
└─────────────────────────────────────────────────────────────┘
```

### 5.2 Redisson 实现

```
Redisson 可重入锁原理：

┌─────────────────────────────────────────────────────────────┐
│  1. 加锁                                                      │
│     ├── Redis SET 命令 NX + PX 参数                            │
│     ├── 设置锁的过期时间（防止死锁）                              │
│     └── 存储锁的持有者信息（防止误删）                            │
│                                                             │
│  2. 可重入                                                    │
│     ├── 同一线程多次加锁，计数器 +1                              │
│     ├── 存储重入次数                                            │
│     └── 解锁时计数器 -1，直到 0 才真正删除                        │
│                                                             │
│  3. 看门狗（Watch Dog）                                       │
│     ├── 锁定成功后启动定时任务                                   │
│     ├── 定期续期（默认30秒）                                    │
│     └── 防止业务未执行完锁已过期                                 │
│                                                             │
│  4. 公平锁                                                    │
│     ├── 基于 Redis 有序集合                                    │
│     └── 按获取锁顺序排队                                        │
│                                                             │
│  5. 联锁（MultiLock）                                        │
│     ├── 多个 Redis 实例组合                                    │
│     └── 提高可靠性                                             │
│                                                             │
│  6. 红锁（RedLock）                                          │
│     ├── N个Redis实例，多数派成功才算成功                          │
│     └── 解决单点故障问题                                        │
└─────────────────────────────────────────────────────────────┘
```

## 6. 分布式ID生成

### 6.1 雪花算法

```
雪花算法结构：

┌─────────────────────────────────────────────────────────────┐
│   符号位(1) | 时间戳(41) | 机器ID(10) | 序列号(12)            │
│   0         |            |            |                      │
│   -         |------------|------------|---------------------│
│   63         62-22         21-12        11-0                  │
│                                                             │
│   时间戳：当前时间相对于epoch的毫秒数                           │
│   epoch：2020-01-01 00:00:00 UTC                             │
│                                                             │
│   机器ID：数据中心(5位) + 机器ID(5位) = 32个节点               │
│                                                             │
│   序列号：同一毫秒内生成的ID序号，4096个/毫秒                   │
│                                                             │
│   时间回拨处理：                                              │
│   ├── 拒绝请求：时间回拨时抛出异常                              │
│   ├── 等待：线程阻塞直到回拨时间过去                            │
│   └── 跳过：记录日志，继续处理                                  │
└─────────────────────────────────────────────────────────────┘
```

### 6.2 改进方案

```
改进的雪花算法：

1. 时间戳优化
   ├── 使用时间戳差值（避免使用绝对时间）
   └── 时间戳精度调整（1ms / 100μs / 10μs）

2. 机器ID优化
   ├── 动态分配机器ID
   ├── ZooKeeper 分配
   └── Redis 分配

3. 序列号优化
   ├── 增加序列号位数（提升QPS）
   └── 时间回拨时序列号补偿

4. 开源方案
   ├── Twitter Snowflake（原始实现）
   ├── leaf（美团）：号段模式 + 雪花算法
   ├── Segment（百度）：号段模式
   └── TinyID（滴滴）：数据库号段模式
```

## 7. 生产环境最佳实践

### 7.1 架构设计原则

```
分布式架构设计原则：

├── 1. 无状态设计
│   ├── 服务本身不保存状态
│   ├── 状态外置到Redis/数据库
│   └── 便于水平扩展和故障转移
│
├── 2. 故障隔离
│   ├── 服务分级：核心服务/非核心服务
│   ├── 资源隔离：线程池/容器隔离
│   └── 降级熔断：Sentinel/Hystrix
│
├── 3. 最终一致性
│   ├── 不强求实时一致
│   ├── 允许短暂不一致
│   └── 通过补偿机制达到一致
│
├── 4. 服务退化
│   ├── 关键服务不可用时降级
│   ├── 提供默认值/缓存数据
│   └── 保证核心功能可用
│
└── 5. 可观测性
    ├── 链路追踪：Jaeger/Zipkin
    ├── 日志采集：ELK/Loki
    └── 监控告警：Prometheus/Grafana
```

### 7.2 常见问题与解决方案

```
分布式系统常见问题：

┌─────────────────────────────────────────────────────────────┐
│  问题1：缓存穿透                                             │
│  ├── 现象：查询不存在的数据，缓存和数据库都查不到               │
│  ├── 解决：布隆过滤器 / 缓存空值                              │
│  └── 布隆过滤器：O(1)查询，有概率误判                         │
│                                                             │
│  问题2：缓存击穿                                             │
│  ├── 现象：热点key过期，大量请求打到数据库                      │
│  ├── 解决：互斥锁 / 永不过期                                  │
│  └── 互斥锁：只让一个线程查DB，其他线程等待                     │
│                                                             │
│  问题3：缓存雪崩                                             │
│  ├── 现象：大量key同时过期，缓存大面积失效                      │
│  ├── 解决：随机过期时间 / 集群部署 / 限流降级                   │
│  └── 随机过期：expire = base + random                         │
│                                                             │
│  问题4：分布式锁失效                                         │
│  ├── 现象：锁已释放但业务未执行完                              │
│  ├── 解决：看门狗机制 / 合理设置过期时间                        │
│  └── Redisson看门狗：30秒续期                                 │
│                                                             │
│  问题5：分布式事务不一致                                     │
│  ├── 现象：部分成功部分失败                                  │
│  ├── 解决：Seata / 可靠消息 / TCC                            │
│  └── 可靠消息：本地事务 + MQ 保证最终一致                       │
│                                                             │
│  问题6：雪崩效应                                             │
│  ├── 现象：级联故障导致系统整体不可用                            │
│  ├── 解决：熔断降级 / 舱壁隔离 / 限流                          │
│  └── 熔断器：Open/Closed/Half-Open 三态                       │
└─────────────────────────────────────────────────────────────┘
```
