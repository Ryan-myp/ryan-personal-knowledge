## ADR-001: 竞价引擎架构选型

**状态**: 已采纳
**日期**: 2026-08-11
**背景**: 需要设计支持实时竞价的高性能DSP系统

### 决策
采用**微服务架构 + 事件驱动**的竞价引擎设计：
- 竞价服务拆分为独立微服务
- 使用 Kafka 作为事件总线
- 引入 Redis 作为缓存层

### 上下文
- 预期 QPS: 100K+
- P99延迟要求: < 50ms
- 需要支持多租户
- 预算控制要求实时性

### 权衡
| 方案 | 优点 | 缺点 |
|------|------|------|
| 单体架构 | 简单、性能好 | 扩展性差、维护难 |
| 微服务架构 | 灵活、可独立扩展 | 运维复杂、延迟略高 |
| 事件驱动 | 解耦、可扩展 | 复杂度增加 |

### 后果
- ✅ 支持水平扩展
- ✅ 各服务独立部署
- ⚠️ 需要运维 Kafka 和 Redis
- ⚠️ 分布式事务处理复杂

### 参考
- 淘宝广告系统架构
- Facebook Audience Network

## ADR-002: 预算控制方案

**状态**: 已采纳
**日期**: 2026-08-11

### 决策
采用 **Redis 原子扣减 + 异步对账** 方案：
1. 竞价时从 Redis 预扣预算
2. 展示后确认扣减
3. 定时任务对账补扣

### 上下文
- 预算控制要求强一致性
- 不能超投
- 需要支持多维度预算（日预算/周预算/总预算）

### 权衡
| 方案 | 优点 | 缺点 |
|------|------|------|
| 数据库事务 | 强一致 | 性能差、并发低 |
| Redis原子操作 | 性能好 | 可能有丢失 |
| 本地消息表 | 可靠 | 复杂度高 |

### 后果
- ✅ 高性能（Redis原子操作）
- ✅ 最终一致（对账补偿）
- ⚠️ 需要处理对账逻辑
- ⚠️ 可能有短暂的预算超投

## ADR-003: 质量分模型选型

**状态**: 已采纳
**日期**: 2026-08-11

### 决策
采用 **LR模型 + 深度学习模型** 的混合方案：
- 实时性要求高的场景用 LR 模型
- 精度要求高的场景用深度学习模型

### 上下文
- 需要实时预测CTR和CVR
- 准确率要求 > 85%
- 推理延迟 < 10ms

### 权衡
| 方案 | 优点 | 缺点 |
|------|------|------|
| LR模型 | 快、简单 | 精度有限 |
| 深度学习 | 精度高 | 慢、复杂 |
| 混合方案 | 平衡 | 运维复杂 |

### 后果
- ✅ 实时性好
- ✅ 精度可接受
- ⚠️ 需要维护两套模型
- ⚠️ 模型更新复杂

## ADR-004: 归因模型选型

**状态**: 已采纳
**日期**: 2026-08-11

### 决策
采用 **Shapley Value + 时间衰减** 的混合归因方案：
- 主要渠道用 Shapley Value
- 长周期转化用时间衰减

### 上下文
- 需要准确归因以优化投放
- 转化周期可能长达 7 天
- 需要支持多渠道归因

### 权衡
| 方案 | 优点 | 缺点 |
|------|------|------|
| 最后点击 | 简单 | 不准确 |
| 首次点击 | 公平 | 不准确 |
| Shapley Value | 准确 | 计算复杂 |
| 时间衰减 | 合理 | 需要调参 |

### 后果
- ✅ 归因更准确
- ✅ 支持多渠道
- ⚠️ 计算成本高
- ⚠️ 需要离线计算

## ADR-005: 反作弊方案

**状态**: 已采纳
**日期**: 2026-08-11

### 决策
采用 **规则引擎 + 机器学习** 的反作弊方案：
- 规则引擎处理已知模式
- 机器学习检测新型攻击

### 上下文
- 广告欺诈损失严重
- 需要实时拦截
- 误杀率要求 < 1%

### 权衡
| 方案 | 优点 | 缺点 |
|------|------|------|
| 纯规则 | 简单、可解释 | 难以应对新型攻击 |
| 纯ML | 准确 | 黑盒、需标注 |
| 混合方案 | 平衡 | 复杂 |

### 后果
- ✅ 拦截率高
- ✅ 误杀率低
- ⚠️ 需要持续训练模型
- ⚠️ 规则维护成本
