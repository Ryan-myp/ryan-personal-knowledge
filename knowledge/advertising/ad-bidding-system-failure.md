## 1. 业务背景

**业务场景**: 广告竞价系统故障排查

该场景在以下业务中存在：
- 电商平台：商品搜索、推荐、下单
- 金融系统：支付、风控、清算
- 广告系统：竞价、归因、反作弊
- 社交系统：Feed流、消息、关系链

## 2. 问题描述

### 2.1 现状分析

系统在运行过程中遇到以下问题：

| 问题类型 | 具体表现 | 影响范围 | 严重程度 |
|----------|----------|----------|----------|
| 性能问题 | P99延迟从10ms升至500ms | 全部用户 | P0 |
| 一致性问题 | 订单状态不一致 | 财务对账 | P0 |
| 可用性问题 | 服务间歇性不可用 | 交易链路 | P1 |
| 扩容问题 | 无法支撑大促流量 | 全系统 | P1 |

### 2.2 根因分析

通过监控和日志分析，发现以下根本原因：

#### 根因1: 数据库连接池耗尽
- **现象**: 大量请求等待数据库连接
- **根因**: 连接池配置不当，最大连接数过小
- **影响**: 请求堆积，延迟飙升

#### 根因2: SQL慢查询
- **现象**: 部分SQL执行时间超过5s
- **根因**: 缺少索引，全表扫描
- **影响**: 数据库CPU占用高

#### 根因3: 缓存穿透
- **现象**: 大量无效key请求穿透到数据库
- **根因**: 缺少布隆过滤器保护
- **影响**: 缓存命中率低，数据库压力大

### 3.2 具体实施

#### 3.2.1 连接池优化
```go
// 原配置（错误）
maxOpenConns: 10
maxIdleConns: 5
connMaxLifetime: 5m

// 优化后配置
maxOpenConns: 200
maxIdleConns: 50
connMaxLifetime: 30m
connMaxIdleTime: 10m

// 读写分离
readerPool: 主库连接池(读)
writerPool: 主库连接池(写)
```

#### 3.2.2 索引优化
```sql
-- 原SQL（全表扫描）
SELECT * FROM orders WHERE user_id = ? AND status = ?

-- 优化后（索引覆盖）
ALTER TABLE orders ADD INDEX idx_user_status (user_id, status)
SELECT id, amount, status FROM orders WHERE user_id = ? AND status = ?

-- 执行计划对比
-- Before: type=ALL, rows=1000000
-- After:  type=ref, rows=100
```

#### 3.2.3 缓存优化
```go
// 布隆过滤器（防止缓存穿透）
bloomFilter := bloom.New(1<<20, 3)
bloomFilter.Add(key)

// 空值缓存（TTL=5min）
if !bloomFilter.MightContain(key) {
    cache.Set(key, nil, 5*time.Minute)
    return nil
}

// 多级缓存（L1+L2）
result, ok := l1Cache.Get(key)  // 本地缓存 <1us
if !ok {
    result, ok = l2Cache.Get(ctx, key)  // Redis <100us
    if ok {
        l1Cache.Set(key, result)  // 回写L1
    }
}
```

## 5. 经验总结

### 5.1 关键决策

| 决策点 | 选项A | 选项B | 选择 | 理由 |
|--------|-------|-------|------|------|
| 缓存方案 | Redis Cluster | Memcached | Redis | 数据结构丰富 |
| 数据库选型 | MySQL | PostgreSQL | MySQL | 团队熟悉+生态 |
| MQ选型 | Kafka | RabbitMQ | Kafka | 高吞吐+持久化 |
| 服务网格 | Istio | Linkerd | Istio | 功能完整 |
| 监控方案 | Prometheus | VictoriaMetrics | Prometheus | CNCF标准 |

### 5.2 踩坑记录

| 问题 | 现象 | 根因 | 解决方案 | 教训 |
|------|------|------|----------|------|
| OOM | 进程被Kill | 内存泄漏 | 检查引用释放 | 定期pprof |
| 高延迟 | P99飙升 | 锁竞争 | 优化锁粒度 | 无锁设计 |
| 数据不一致 | 对账不平 | 副本不同步 | 检查ISR | 异步转同步 |
| 缓存雪崩 | 全部失效 | TTL相同 | 随机TTL | 分散过期 |

### 5.3 最佳实践

1. **监控先行**: 先建立完善的监控体系，再上线新功能
2. **容量规划**: 提前预估流量，预留3倍扩容空间
3. **灰度发布**: 新功能灰度发布，观察指标后再全量
4. **故障演练**: 定期做混沌工程，验证系统容错能力
5. **文档沉淀**: 故障处理和解决方案必须沉淀为文档
