## 第一部分：系统设计方法论

### 系统设计思考框架

```
系统设计五步法：

┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  Step 1: 需求澄清 (Requirements Clarification)                      │

│  Step 2: 高层设计 (High-Level Design)                               │
│  ├── 组件划分：核心模块识别                                         │
│  ├── 接口定义：模块间通信协议                                       │
│  ├── 数据流：数据如何流转                                           │
│  └── 技术选型：数据库、中间件选择                                    │
│                                                                     │
│  Step 3: 详细设计 (Detailed Design)                                 │
│  ├── 数据结构：核心表结构设计                                       │
│  ├── 算法设计：关键算法实现                                         │
│  ├── 接口设计：API 详细规范                                         │
│  └── 并发设计：锁、事务、一致性                                      │
│                                                                     │
│  Step 4: 容量规划 (Capacity Planning)                               │
│  ├── 流量估算：峰值 QPS、日活                                       │
│  ├── 存储估算：数据量、增长趋势                                     │
│  ├── 带宽估算：网络流量                                             │
│  └── 成本估算：服务器、云资源                                       │
│                                                                     │
│  Step 5: 瓶颈分析与优化 (Bottleneck Analysis)                       │
│  ├── 单点故障：冗余设计                                             │
│  ├── 性能瓶颈：缓存、异步、分片                                     │
│  ├── 可扩展性：水平扩展能力                                         │
```

### 核心权衡 (Trade-offs)

```
CAP 定理在实际系统中的应用：

┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  一致性 (Consistency) vs 可用性 (Availability) vs 分区容忍性        │
│  (Partition Tolerance)                                               │
│                                                                     │
│  系统类型选择：                                                       │
│  ├── CP 系统：分布式数据库 (ZooKeeper, Redis Cluster)               │
│  ├── AP 系统：缓存 (Memcached, DynamoDB)                            │
│  └── PACELC：延迟优先选可用性，一致性优先选一致性                    │
│                                                                     │
│  实际选择依据：                                                       │
│  ├── 金融交易系统：CP（强一致性）                                   │
│  ├── 社交 feed 流：AP（最终一致性）                                 │
│  ├── 电商库存：CP（防止超卖）                                       │
│  └── 广告竞价：AP（高可用优先）                                     │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 第二部分：分布式系统核心问题

### 分布式一致性模型

```
一致性模型对比：

┌──────────────┬────────────┬────────────┬────────────┐
│    模型      │  一致性    │  可用性    │  适用场景  │
├──────────────┼────────────┼────────────┼────────────┤
│ 强一致性     │ 最高       │ 最低       │ 金融交易   │
│ 弱一致性     │ 最低       │ 最高       │ 缓存       │
│ 最终一致性   │ 中等       │ 高         │ 社交动态   │
│ 因果一致性   │ 较高       │ 较高       │ 协作系统   │
│ 会话一致性   │ 中等       │ 高         │ 用户会话   │
└──────────────┴────────────┴────────────┴────────────┘

实现方案：
├─ 强一致性：Paxos / Raft / ZAB
├─ 最终一致性：Gossip / CRDT / 消息队列
└─ 因果一致性：Vector Clock / Lamport Timestamp
```

### 分布式锁实现

```go
// 基于 Redis 的分布式锁
type RedisLock struct {
    client *redis.Client
    key    string
    value  string
    ttl    time.Duration
}

func (l *RedisLock) Acquire() bool {
    // SET key value NX PX ttl
    result, err := l.client.Set(
        context.Background(),
        l.key,
        l.value,
        redis.ET,
        "NX",
        "PX",
        l.ttl,
    ).Result()
    return result == "OK"
}

func (l *RedisLock) Release() bool {
    // 使用 Lua 脚本保证原子性
    script := `
        if redis.call("get", KEYS[1]) == ARGV[1] then
            return redis.call("del", KEYS[1])
        else
            return 0
        end
    `
    result, _ := l.client.Eval(script, []string{l.key}, l.value).Int()
    return result == 1
}

// 应用：广告预算扣减、库存锁定
```

### 缓存架构设计

```
缓存分层架构：

┌─────────────────────────────────────────────────────────────────────┐
│                     缓存层次结构                                     │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  L1: 本地缓存 (Local Cache)                                         │
│  ├── 实现：sync.Map / singleflight                                  │
│  ├── 特点：零网络开销，进程内访问                                    │
│  ├── 限制：数据不一致风险，内存有限                                  │
│  └── 适用：热点数据、读多写少                                       │
│                                                                     │
│  L2: 分布式缓存 (Distributed Cache)                                 │
│  ├── 实现：Redis Cluster / Memcached                               │
│  ├── 特点：数据共享，持久化支持                                     │
│  ├── 限制：网络开销，一致性维护                                     │
│  └── 适用：业务缓存，会话存储                                       │
│                                                                     │
│  L3: 数据库 (Database)                                              │
│  ├── 实现：MySQL / PostgreSQL / TiDB                               │
│  ├── 特点：持久化，事务保证                                         │
│  └── 适用：主数据存储                                               │
│                                                                     │
│  L4: 持久化存储 (Persistent Storage)                                │
│  ├── 实现：HDFS / S3 / OSS                                         │
│  ├── 特点：海量存储，低成本                                         │
│  └── 适用：离线分析，备份恢复                                       │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 实践应用

### 场景 1: 设计广告竞价系统

1. **需求分析**：
   - QPS: 100万+/s
   - 延迟: P99 < 100ms
   - 一致性: 最终一致性可接受

2. **架构设计**：
   - 计算节点：无状态服务，水平扩展
   - 用户画像：Redis 集群 + 本地缓存
   - 模型推理：GPU 集群 + 模型服务化
   - 数据流：Kafka 实时消息

3. **关键设计**：
   - 分片路由：按广告主分片
   - 降级策略：画像降级 → 规则出价 → 默认出价
   - 预算追踪：本地缓存 + 异步同步

### 场景 2: 设计 Agent 记忆系统

1. **需求分析**：
   - 支持跨会话记忆
   - 语义检索能力
   - 低延迟查询

2. **架构设计**：
   - 短期记忆：内存存储，快速访问
   - 长期记忆：向量数据库，语义检索
   - 混合检索：向量 + 关键词 RRF 融合

3. **关键设计**：
   - Embedding 模型选择
   - 向量数据库选型（Milvus vs pgvector）
   - 记忆压缩与更新策略

## 自测题

<details>
<summary>Q1: 为什么分布式系统需要 CAP 权衡？</summary>

**答案**：
1. **网络不可靠**：分布式系统中网络分区是常态
2. **一致性冲突**：分区时，要么放弃一致性（AP），要么放弃可用性（CP）
3. **实际需求**：不同场景对一致性和可用性的要求不同
4. **PACELC 扩展**：无分区时，也要在延迟和一致性之间权衡
</details>

<details>
<summary>Q2: 缓存穿透、击穿、雪崩的区别是什么？</summary>

**答案**：
| 问题 | 原因 | 解决方案 |
|------|------|---------|
| 穿透 | 查询不存在的数据 | 布隆过滤器、缓存空值 |
| 击穿 | 热点 key 过期 | 互斥锁、永不过期 |
| 雪崩 | 大量 key 同时过期 | 随机过期时间、集群部署 |
</details>

<details>
<summary>Q3: 如何设计一个高可用的分布式锁？</summary>

**答案**：
1. **原子性**：SET NX PX 保证原子获取
2. **安全性**：Lua 脚本保证原子释放
3. **可重入**：记录持有者和重入次数
4. **看门狗**：自动续期防止业务未结束锁过期
5. **高可用**：Redis Cluster 多副本
</details>
