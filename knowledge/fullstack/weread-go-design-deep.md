## 第一部分：Go 运行时架构

### Goroutine 调度器 (GMP)

```
Go 调度器架构：

┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│                        GMP 模型                                     │
│                                                                     │
│  ┌──────────┐    ┌──────────┐    ┌──────────┐                      │
│  │   G      │    │   M      │    │   P      │                      │
│  │ (Gorouti-│    │ (Machine)│    │(Processor)│                      │
│  │  ne)     │    │          │    │          │                      │
│  ├──────────┤    ├──────────┤    ├──────────┤                      │
│  │ 状态     │    │ OS线程   │    │ 本地队列 │                      │
│  │ 参数     │    │ 执行体   │    │ 最大256  │                      │
│  │ 栈      │    │          │    │          │                      │
│  └────┬─────┘    └────┬─────┘    └────┬─────┘                      │
│       │               │               │                            │
│       └───────────────┼───────────────┘                            │
│                       ▼                                             │
│              ┌─────────────────┐                                   │
│              │  Global Queue   │                                   │
│              │  (全局队列)     │                                   │
│              └────────┬────────┘                                   │
│                       │                                             │
│              ┌────────┴────────┐                                   │
│              │   Work Stealing  │                                   │
│              │  (工作窃取机制)  │                                   │
│              └─────────────────┘                                   │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘

调度流程：
1. M 从 P 的 local queue 取 G 执行
2. local queue 空时，从 global queue 取
3. 仍为空时，尝试从其他 P 窃取一半 G
4. 全局空时，M 进入休眠等待新任务
```

### 内存分配器

```
Go 内存分配层级：

┌─────────────────────────────────────────────────────────────────────┐
│                        内存分配层级                                 │
├─────────────────────────────────────────────────────────────────────┤
│                                                                     │
│  Level 1: mcache (每 P 私有缓存)                                    │
│  ├── 避免锁竞争，提升性能                                           │
│  ├── 每个 P 维护多个 mcache                                        │
│  └── 对象大小分级，不同 size class 对应不同 mspan                   │
│                                                                     │
│  Level 2: mcentral (中等对象管理)                                   │
│  ├── 管理 8KB-32MB 的对象                                          │
│  ├── 按 size class 分组管理                                        │
│  └── mcache 向 mcentral 申领/归还 span                              │
│                                                                     │
│  Level 3: mheap (大对象管理)                                        │
│  ├── 管理 >32MB 的大对象                                           │
│  ├── 直接通过 mmap 分配                                             │
│  └── 不走 tcmalloc 分级管理                                        │
│                                                                     │
│  Level 4: OS 层面                                                   │
│  ├── 通过 mmap/munmap 与操作系统交互                                │
│  └── 使用虚拟内存，不直接操作物理内存                                │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 第二部分：垃圾回收 (GC)

### 三色标记法

```
GC 三色标记算法：

┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  颜色定义：                                                         │
│  ├── 白色 (White)：未被 GC 扫描过的对象                              │
│  ├── 灰色 (Gray)：已被扫描，但其引用对象尚未完全扫描                │
│  └── 黑色 (Black)：已被扫描，且其引用对象也已完全扫描                │
│                                                                     │
│  标记过程：                                                         │
│  1. 初始：所有对象为白色                                           │
│  2. 根对象标记为灰色                                              │
│  3. 从灰色对象中取一个，扫描其引用的对象：                           │
│     ├── 引用对象为白色 → 标记为灰色，加入队列                       │
│     └── 引用对象已为灰色/黑色 → 不做处理                            │
│  4. 当前对象标记为黑色                                             │
│  5. 重复 3-4 直到队列为空                                          │
│  6. 回收所有白色对象                                               │
│                                                                     │
│  写屏障 (Write Barrier)：                                           │
│  ├── 目的：防止 concurrent mark 期间对象被误回收                    │
│  ├── 类型：点写屏障、混写入屏障                                     │
│  └── Go 1.8+ 使用混写入屏障 (Mixed-write barrier)                  │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

### GC 触发条件

```go
// Go GC 触发逻辑伪代码
func gcTrigger() bool {
    // 条件1：内存增长超过阈值
    if memstats.heap_alloc > memstats.last_gc_alloc * (1 + GOGC/100) {
        return true
    }
    // 条件2：时间间隔过长
    if time.Since(memstats.last_gc_time) > gcPauseMaxDuration {
        return true
    }
    return false
}

// 关键配置
// GOGC=100: 默认值，内存增长 100% 时触发 GC
// GOGC=50:  更频繁 GC，减少内存占用
// GOGC=200: 更少 GC，减少 CPU 开销
```

## 第三部分：网络模型

### Netpoller 事件驱动

```
Go 网络模型 (io_uring/epoll/kqueue):

┌─────────────────────────────────────────────────────────────────────┐
│                                                                     │
│  Netpoller 架构：                                                   │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  Event Poller (后台线程)                                      │   │
│  │  ├── epoll_wait / kqueue / io_uring                          │   │
│  │  └── 监听所有 fd 的读写事件                                   │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                          │                                          │
│                          ▼                                          │
│  ┌─────────────────────────────────────────────────────────────┐   │
│  │  netpollready (唤醒 G)                                        │   │
│  │  ├── 将 G 加入 P 的 local queue                               │   │
│  │  └── 通知对应的 M 去执行                                       │   │
│  └─────────────────────────────────────────────────────────────┘   │
│                                                                     │
│  典型流程：                                                         │
│  1. Go routine 发起网络请求 → 阻塞，G 进入等待                      │
│  2. Netpoller 检测到 fd 可读 → 唤醒对应 G                           │
│  3. G 被放入 P 的 local queue → M 取出执行                          │
│  4. 请求完成，G 阻塞 → 再次进入等待                                 │
│                                                                     │
└─────────────────────────────────────────────────────────────────────┘
```

## 自测题

<details>
<summary>Q1: Go 的 GMP 调度模型相比传统的 M:N 调度有什么优势？</summary>

**答案**：
1. **工作窃取**：P 之间可以窃取任务，负载均衡
2. **本地队列**：减少锁竞争，提升缓存命中率
3. **M 与 G 解耦**：M 可以执行不同 G，提高利用率
4. **协作式抢占**：避免饥饿，保证 fairness
</details>

<details>
<summary>Q2: 为什么 Go 使用三色标记法而不是其他 GC 算法？</summary>

**答案**：
1. **暂停时间短**：mark 阶段可以并发执行
2. **实现简单**：相比分代 GC、区域 GC 更简单
3. **内存友好**：不需要额外的内存区域划分
4. **写屏障成熟**：混写入屏障效果好，开销可控
</details>

<details>
<summary>Q3: Go 的零拷贝网络 IO 是如何实现的？</summary>

**答案**：
1. **epoll/kqueue 边缘触发**：减少系统调用次数
2. **io_uring (Go 1.22+)**：异步 IO，用户态轮询
3. **Buffer Pool**：sync.Pool 复用 byte slice
4. **ReadMessageBuffer**：Zero-copy 读取 UDP 消息
</details>
