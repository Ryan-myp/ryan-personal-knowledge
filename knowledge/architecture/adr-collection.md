## ADR-001: 竞价引擎技术选型 — Go vs Java

### 背景
广告竞价系统要求 P99 < 50ms，QPS 10 万+，现有 Java 方案延迟不稳定。

### 选项
| 选项 | 延迟 | 吞吐量 | 内存占用 | 开发效率 |
|------|------|--------|----------|----------|
| Go | 20-30ms | 高 | 低 | 中 |
| Java + Spring | 50-100ms | 中 | 高 | 高 |
| Rust | 10-20ms | 高 | 低 | 低 |
| C++ | 10-20ms | 极高 | 低 | 低 |

### 决策
选择 **Go**。

### 理由
1. **延迟可控**：Go 调度器确定性强，无 GC 长暂停
2. **开发效率**：比 Rust/C++ 快 3-5 倍
3. **生态完善**：gRPC、Prometheus 支持好
4. **运维简单**：单二进制部署，无 JVM 调优

### 权衡
- 放弃了 Java 丰富的 Spring 生态
- 需要自己实现部分功能（如配置中心）

## ADR-002: 数据库选型 — MySQL vs ClickHouse

### 背景
广告归因数据量快速增长，MySQL 查询延迟从 100ms 升至 5s。

### 选项
| 选项 | 写入吞吐 | 查询延迟 | 存储成本 | 复杂度 |
|------|----------|----------|----------|--------|
| MySQL | 低 | 高(大数据) | 高 | 低 |
| ClickHouse | 极高 | 低 | 低 | 中 |
| Doris | 高 | 低 | 中 | 中 |
| ES | 中 | 低(模糊) | 高 | 中 |

### 决策
选择 **ClickHouse** 作为归因分析引擎，MySQL 保留核心交易数据。

### 理由
1. **分析型负载**：ClickHouse 专为 OLAP 设计
2. **压缩率高**：列式存储，节省 70% 存储
3. **SQL 兼容**：降低迁移成本
4. **实时性**：支持近实时聚合

### 权衡
- 放弃 MySQL 的 ACID 事务
- 需要学习 ClickHouse 特有的 SQL 语法

## ADR-003: 缓存策略 — Redis vs Memcached

### 背景
竞价请求频繁查询用户画像，需要高性能缓存。

### 选项
| 选项 | 数据结构 | 持久化 | 集群方案 | 延迟 |
|------|----------|--------|----------|------|
| Redis | 丰富 | 支持 | Redis Cluster | 0.1ms |
| Memcached | 简单 | 不支持 | 客户端分片 | 0.05ms |

### 决策
选择 **Redis Cluster**。

### 理由
1. **数据结构**：Hash、ZSet、Bitmap 适合广告场景
2. **持久化**：AOF 防止数据丢失
3. **功能丰富**：Lua 脚本支持复杂逻辑
4. **生态成熟**：监控、运维工具完善

### 权衡
- 比 Memcached 延迟高 0.05ms（可接受）
- 运维复杂度增加

## ADR-004: 消息队列选型 — Kafka vs RabbitMQ

### 背景
竞价日志需要高吞吐写入，后续批量消费。

### 选项
| 选项 | 吞吐 | 延迟 | 可靠性 | 复杂度 |
|------|------|------|--------|--------|
| Kafka | 极高 | 高 | 中 | 中 |
| RabbitMQ | 中 | 低 | 高 | 低 |
| Pulsar | 高 | 中 | 高 | 高 |

### 决策
选择 **Kafka**。

### 理由
1. **吞吐需求**：竞价日志 QPS 50 万+
2. **持久化**：日志需要保留 7 天
3. **生态**：Kafka Streams 支持实时处理
4. **社区活跃**：问题容易找到解决方案

### 权衡
- 消息延迟较高（毫秒级）
- 运维复杂度高于 RabbitMQ

## ADR-005: 服务网格选型 — Istio vs Linkerd

### 背景
微服务数量增长到 200+，需要服务治理。

### 选项
| 选项 | 功能丰富度 | 性能开销 | 学习曲线 | Kubernetes 集成 |
|------|-----------|----------|----------|-----------------|
| Istio | 极高 | 中 | 高 | 原生 |
| Linkerd | 中 | 低 | 低 | 原生 |
| Envoy Gateway | 高 | 低 | 中 | 原生 |

### 决策
选择 **Linkerd**（初期）→ 后续升级为 **Istio**。

### 理由
1. **简单起步**：Linkerd 部署简单，性能开销低
2. **渐进式**：业务增长后再升级到 Istio
3. **Kubernetes 友好**：官方支持 Kubernetes

### 权衡
- 初期功能受限（如无细粒度流量控制）
- 后期迁移成本

## ADR-006: 配置中心选型 — Apollo vs Nacos

### 背景
微服务配置管理混乱，需要统一配置中心。

### 选项
| 选项 | 配置类型 | 实时推送 | 权限管理 | 运维复杂度 |
|------|----------|----------|----------|-----------|
| Apollo | 高 | 实时 | 完善 | 中 |
| Nacos | 中 | 实时 | 一般 | 低 |
| Consul | 低 | 手动 | 完善 | 中 |

### 决策
选择 **Apollo**。

### 理由
1. **权限完善**：支持项目级、环境级权限
2. **灰度发布**：支持配置灰度
3. **审计日志**：配置变更可追溯
4. **社区活跃**：携程开源，问题响应快

### 权衡
- 比 Nacos 复杂
- 需要独立部署

## ADR-007: 日志方案 — ELK vs Loki

### 背景
系统日志量增长到 10GB/天，需要高效检索。

### 选项
| 选项 | 存储成本 | 查询性能 | 运维复杂度 | 生态 |
|------|----------|----------|-----------|------|
| ELK | 高 | 高 | 高 | 完善 |
| Loki | 低 | 中 | 低 | 发展中 |
| ClickHouse | 低 | 高 | 中 | 完善 |

### 决策
选择 **Loki + Grafana**。

### 理由
1. **成本低**：只存索引，不存日志内容
2. **集成简单**：与 Prometheus 标签体系一致
3. **查询够用**：日志量不是特别大时足够
4. **运维简单**：无 Elasticsearch 调优负担

### 权衡
- 复杂查询性能不如 ELK
- 日志内容需要单独存储（如 S3）

## ADR-008: 可观测性方案 — Prometheus + Jaeger vs Datadog

### 背景
需要统一的监控告警和链路追踪。

### 选项
| 选项 | 自托管 | 成本 | 功能完整性 | 学习成本 |
|------|--------|------|-----------|----------|
| Prometheus + Jaeger | 是 | 低 | 高 | 高 |
| Datadog | 否 | 高 | 极高 | 低 |
| New Relic | 否 | 高 | 高 | 低 |

### 决策
选择 **Prometheus + Jaeger + Grafana** 自托管。

### 理由
1. **成本可控**：避免云厂商锁定
2. **数据私有**：敏感数据不出内网
3. **生态成熟**：Prometheus 是云原生标准
4. **灵活定制**：可以深度定制

### 权衡
- 运维成本高（需要专人维护）
- 功能不如 Datadog 完善

## ADR-009: 容器编排 — Kubernetes vs Docker Swarm

### 背景
需要容器化部署，选择编排方案。

### 选项
| 选项 | 功能 | 学习曲线 | 生态 | 社区 |
|------|------|----------|------|------|
| Kubernetes | 极强 | 高 | 极强 | 极强 |
| Docker Swarm | 中 | 低 | 中 | 一般 |
| Nomad | 高 | 中 | 中 | 一般 |

### 决策
选择 **Kubernetes**。

### 理由
1. **行业标准**：招聘容易，资料丰富
2. **功能强大**：HPA、滚动更新、配置管理
3. **生态完善**：Helm、Istio、Prometheus 都支持
4. **云厂商支持**：AWS EKS、GCP GKE 成熟

### 权衡
- 学习曲线陡峭
- 运维成本高

## ADR-010: 域名解析 — DNS vs Service Mesh DNS

### 背景
微服务间调用需要稳定的 DNS 解析。

### 选项
| 选项 | 延迟 | 可靠性 | 复杂度 | 适用场景 |
|------|------|--------|--------|----------|
| 外部 DNS | 高 | 中 | 低 | 少量服务 |
| CoreDNS | 中 | 高 | 中 | K8s 环境 |
| Service Mesh | 低 | 高 | 高 | 大规模微服务 |

### 决策
选择 **CoreDNS + Service Mesh 双模式**。

### 理由
1. **过渡方案**：先上 CoreDNS，后续按需升级
2. **成本平衡**：不过早引入 Service Mesh
3. **灵活性**：CoreDNS 支持自定义插件

### 权衡
- 双模式增加运维复杂度
- 后续迁移需要规划

## 总结：架构决策原则

### 决策框架
```
1. 明确问题：我们解决什么问题？
2. 列出选项：有哪些可行方案？
3. 评估标准：成本、性能、复杂度、生态
4. 做出决策：选择最优方案
5. 记录理由：为什么选这个？
6. 定期回顾：决策是否需要调整？
```

### 常见反模式
- ❌ 盲目追新：新技术一定适合吗？
- ❌ 过度设计：现在需要这么复杂吗？
- ❌ 从众心理：别人用我们就用？
- ❌ 单一 vendor：是否会被绑定？
