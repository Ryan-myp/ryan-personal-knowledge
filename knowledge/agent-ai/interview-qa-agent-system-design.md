## 一、Agent 系统设计面试高频题

### Q1: 如何设计一个生产级 AI Agent 系统？

```
回答框架:
├─ 架构分层
│   ├─ 接口层: MCP/Function Calling/WebSocket
│   ├─ 控制层: 编排引擎 + 策略路由
│   ├─ 执行层: LLM + Tool Executor
│   └─ 记忆层: 工作/短期/长期记忆
│
├─ 关键组件
│   ├─ 工具注册与发现系统
│   ├─ 智能调用选择器
│   ├─ 并行执行引擎
│   ├─ 结果缓存与熔断
│   └─ 可观测性体系
│
├─ 生产要求
│   ├─ 延迟: P99 < 5s, 首 Token < 500ms
│   ├─ 成本: 每请求 <$0.01
│   ├─ 可靠性: 99.9% 可用性
│   └─ 安全: 四层防护 + 审计日志
│
└─ 参考架构
    └─ LangGraph / CrewAI / AutoGen
```

### Q2: 如何处理 Agent 的工具爆炸问题？

```
问题: 100+ 工具时，LLM 选择效率低、上下文占用多

解决方案:
├─ 1. 工具分组 + 两级路由
│   ├─ 第一级: 类别选择 (4-6个类别)
│   ├─ 第二级: 工具选择 (每个类别 5-10 个)
│   └─ 效果: 上下文减少 70%
│
├─ 2. 语义路由 + 向量索引
│   ├─ 预计算工具描述 embedding
│   ├─ 查询时匹配 Top-K 工具
│   └─ 效果: 候选集从 100 → 10
│
├─ 3. 历史权重学习
│   ├─ 记录各工具的成功率
│   ├─ 根据场景动态调整权重
│   └─ 效果: 准确率达到 85%+
│
└─ 4. 工具热缓存
    ├─ 最近使用的工具优先展示
    └─ 效果: 减少 LLM 搜索空间
```

### Q3: 如何设计 Agent 的记忆系统？

```
三层架构:
├─ 工作记忆 (Working Memory)
│   ├─ 实现: 对话上下文窗口
│   ├─ 容量: 4K-128K tokens
│   ├─ 寿命: 会话级别
│   └─ 操作: 直接追加/截断
│
├─ 短期记忆 (Short-Term Memory)
│   ├─ 实现: Qdrant/Milvus 向量库
│   ├─ 容量: 10万+ 条
│   ├─ 寿命: 天-周级别
│   ├─ 操作: 语义检索 + TTL 过期
│   └─ 特点: 自动遗忘
│
├─ 长期记忆 (Long-Term Memory)
│   ├─ 实现: 混合检索 (向量+关键词+图谱)
│   ├─ 容量: 无限
│   ├─ 寿命: 永久
│   ├─ 操作: RRF 融合排序
│   └─ 特点: 主动巩固
│
└─ 遗忘机制
    ├─ Ebbinghaus 遗忘曲线
    ├─ 重要性评分 < 阈值则遗忘
    └─ 定期清理低价值记忆
```

### Q4: 如何优化 Agent 的 Token 成本？

```
成本构成:
├─ LLM 调用: 60-80%
├─ 工具调用: 10-20%
├─ 嵌入模型: 5-10%
└─ 其他: <5%

优化策略:
├─ 1. 上下文管理
│   ├─ 滑动窗口: 保留最近 N 轮对话
│   ├─ 摘要压缩: 旧对话转摘要
│   └─ 选择性注入: 只注入相关记忆
│
├─ 2. 模型选择
│   ├─ 简单任务: 用小模型 (Haiku/GPT-4o-mini)
│   ├─ 复杂推理: 用大模型 (Opus/GPT-4o)
│   └─ 路由决策: 基于任务复杂度自动选择
│
├─ 3. 缓存策略
│   ├─ 工具结果缓存: 相同输入复用结果
│   ├─ LLM 响应缓存: 相似问题复用答案
│   └── RAG 片段缓存: 热门文档常驻内存
│
└─ 4. 批量处理
    ├─ 合并相似查询
    ├─ 并行工具调用
    └── 流式输出降低首 token 延迟
```

## 二、广告系统面试高频题

### Q5: 如何设计高并发电商广告竞价系统？

```
架构:
├─ 请求接入: API Gateway + 限流
├─ 实时特征: Redis Cluster + Flink CEP
├─ 召回排序: Elasticsearch + DeepFM
├─ 竞价引擎: gRPC + C++ 核心
├─ 频控去重: Redis ZSet + Bloom Filter
└─ 数据回流: Kafka → ClickHouse → DB

关键指标:
├─ QPS: 10万+ (峰值50万)
├─ 延迟: P99 < 50ms (竞价) / < 200ms (全链路)
├─ 准确率: pCTR AUC > 0.75
└─ 可用性: 99.99%

核心难点:
├─ 特征新鲜度: 1秒内更新
├─ 模型延迟: < 5ms (TensorRT 优化)
├─ 竞价实时性: 20ms 内完成
└── 频控准确性: 100% 不超频
```

### Q6: RTA 和 RTB 有什么区别？如何设计？

```
RTA (Real-Time API):
├─ 方向: DSP → 媒体平台
├─ 目的: 过滤低价值用户
├─ 策略: 白名单过滤 (命中则排除)
├─ 延迟: < 20ms
├─ 数据: 使用自有用户数据
└─ 隐私: 不暴露用户 ID

RTB (Real-Time Bidding):
├─ 方向: SSP → DSP (通过 Exchange)
├─ 目的: 竞价获取广告位
├─ 策略: 出价 + 频次控制
├─ 延迟: < 100ms
├─ 数据: 使用第三方 DMP
└─ 隐私: 符合 GDPR/CCPA

设计要点:
├─ RTA: 特征匹配服务 + 缓存预热
├─ RTB: 竞价引擎 + 预算 pacing
└─ 组合: RTA 过滤 → RTB 竞价
```

## 三、Go 系统面试高频题

### Q7: Go 中如何避免 GC 停顿过长时间？

```
GC 类型与停顿:
├─ Concurrent Mark: < 1ms (并发)
├─ GC cycle stop-the-world: 10-100ms
└─ Large object allocation: 同步分配

优化策略:
├─ 1. 对象生命周期管理
│   ├─ 使用对象池 (sync.Pool) 复用
│   ├─ 避免在大对象上频繁分配
│   └─ 及时释放不再需要的引用
│
├─ 2. 内存布局优化
│   ├─ 结构体对齐减少 padding
│   ├─ 使用 []byte 而非 string 避免复制
│   └─ 避免不必要的 interface 装箱
│
├─ 3. 分配器调优
│   ├─ GOGC 调整 (默认 100)
│   ├─ MallocStats 监控
│   └── mprof 分析分配热点
│
└─ 4. 工具链
    ├─ go tool trace
    ├─ pprof -gc
    └── benchmark 对比
```

### Q8: 如何设计一个高可用的分布式缓存系统？

```
架构:
├─ 分片层: Consistent Hashing + 虚拟节点
├─ 复制层: Master-Slave + Raft 一致性
├─ 缓存层: LRU + LFU 混合淘汰
├─ 持久层: RDB 快照 + AOF 日志
└─ 故障转移: Sentinel 自动选举

一致性保证:
├─ Read Your Writes: 同一客户端读到自己写的
├─ Monotonic Read: 单调读取，不后退
└─ Eventual Consistency: 最终一致

高可用设计:
├─ 多副本: 3 副本 + Quorum 读写
├─ 故障切换: < 30s 自动切换
├─ 数据恢复: AOF 重写 + BGSAVE
└─ 容量弹性: 在线分片迁移
```
