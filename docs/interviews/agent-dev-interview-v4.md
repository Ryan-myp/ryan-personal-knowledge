## 第一部分：基础问答（15min）

### Java 方向（选做）

**Q1: Java 内存模型有哪些区域？各自的作用是什么？**（3min）

**期望回答**:
| 区域 | 作用 |
|------|------|
| 堆（Heap） | 存放对象实例，GC 主要区域 |
| 栈（Stack） | 存放局部变量、方法调用 |
| 方法区 | 存放类信息、常量、静态变量 |
| 程序计数器 | 记录当前执行的字节码行号 |
| 本地方法栈 | Native 方法服务 |

**追问**: "对象什么时候会被 GC 回收？" → 引用计数 + 可达性分析

---

**Q2: Java 的集合框架有哪些核心接口？HashMap 的实现原理是什么？**（5min）

**期望回答**:
- **核心接口**: Collection（List、Set）、Map
- **HashMap 原理**: 数组 + 链表 + 红黑树（JDK 8+）
  - 哈希冲突：链表存储，长度 > 8 转为红黑树
  - 扩容：2 倍扩容，重新 hash 分布

```java
// HashMap 关键参数
transient Node<K,V>[] table;      // 数组
int threshold;                      // 扩容阈值 = capacity * loadFactor
float loadFactor = 0.75f;           // 负载因子
```

**追问**:
- "ConcurrentHashMap 如何保证线程安全？" → CAS + synchronized + volatile
- "HashMap 和 Hashtable 的区别？" → 线程安全、null 支持、迭代器 Fail-Fast

**Q3: Java 的并发工具有哪些？线程池的参数有哪些？**（5min）

**期望回答**:
| 并发工具 | 作用 |
|---------|------|
| synchronized | 内置锁，方法/代码块级别 |
| ReentrantLock | 显式锁，可中断、公平锁 |
| ConcurrentHashMap | 线程安全 HashMap |
| CompletableFuture | 异步编程 |
| CountDownLatch | 等待其他线程完成 |
| CyclicBarrier | 多线程互相等待 |
| Semaphore | 限流 |

**线程池参数**:
```java
ThreadPoolExecutor(
    corePoolSize,      // 核心线程数
    maximumPoolSize,   // 最大线程数
    keepAliveTime,     // 非核心线程空闲存活时间
    unit,              // 时间单位
    workQueue,         // 任务队列（ArrayBlockingQueue/LinkedBlockingQueue）
    threadFactory,     // 线程工厂
    handler            // 拒绝策略（Abort/CallerRuns/Discard/DiscardOldest）
);
```

**追问**:
- "如何确定线程池大小？" → CPU 密集型：N+1；IO 密集型：2N
- "队列满了怎么办？" → 触发拒绝策略

**Q4: Java 的 GC 算法有哪些？G1 GC 的特点是什么？**（2min）

**期望回答**:
| GC 算法 | 特点 |
|--------|------|
| 标记-清除 | 产生碎片 |
| 复制 | 浪费一半空间 |
| 标记-整理 | 移动对象开销大 |

**G1 GC 特点**:
- 分区管理（Region），避免全堆扫描
- 可预测停顿时间（Goal-based）
- 并发标记，减少 STW
- 优先回收价值最高的 Region

### Go 方向（选做）

**Q1: Go 的 Goroutine 和线程有什么区别？**（3min）

**期望回答**:
| 特性 | Goroutine | 系统线程 |
|------|-----------|---------|
| 初始栈大小 | 2KB | 几 MB |
| 调度方式 | M:N 用户态调度 | 内核调度 |
| 创建开销 | 极小（字节级） | 较大 |
| 切换开销 | 小 | 大（内核态切换） |

**GMP 模型**:
- **G**: Goroutine
- **M**: Machine（OS 线程）
- **P**: Processor（逻辑处理器，维护 runnable G 队列）

---

**Q2: Go 的 Channel 如何实现？select 语句的工作原理？**（5min）

**期望回答**:
- **Channel 实现**: 环形队列 + 锁 + 等待队列
- **select 原理**: 同时监听多个 Channel，随机选择一个就绪的执行

```go
// select 语句示例
select {
case msg := <-ch1:
    fmt.Println("Received", msg)
case ch2 <- data:
    fmt.Println("Sent")
case <-time.After(time.Second):
    fmt.Println("Timeout")
default:
    fmt.Println("No ready channel")
}
```

**追问**:
- "Channel 如何做到安全？" → 互斥锁 + 条件变量
- "无缓冲 vs 有缓冲 Channel 的区别？" → 无缓冲需要双方就绪，有缓冲可临时存储

**Q3: Go 的接口机制是什么？空接口怎么用？**（4min）

**期望回答**:
- **接口实现**: 鸭子类型（隐式实现），不需要 implements 关键字
- **接口存储**: 类型指针 + 值指针（iface 结构体）
- **空接口 interface{}**: 可存储任意类型，常用 type assertion / type switch

```go
// 空接口示例
func printType(v interface{}) {
    switch v.(type) {
    case int:
        fmt.Println("int:", v)
    case string:
        fmt.Println("string:", v)
    default:
        fmt.Println("unknown:", v)
    }
}
```

**Q4: Go 的 GC 是什么算法？与 Java GC 有什么区别？**（3min）

**期望回答**:
- **Go GC**: 混合写屏障 + 三色标记 + 后台并发
- **与 Java 区别**:
  - Go: STW 时间短（< 1ms），并发标记
  - Java: G1/ZGC 也并发，但更复杂

### 通用基础题

**Q5: TCP 三次握手和四次挥手的过程？为什么是三次不是两次？**（3min）

**期望回答**:
```
三次握手:
Client                    Server
  |--- SYN (seq=x) ------->|
  |<-- SYN+ACK (seq=y,ack=x+1) --|
  |--- ACK (ack=y+1) ----->|

为什么不是两次？
- 防止已失效的连接请求报文段突然传到服务端
- 确保双方都能收发，确认序列号初始值
```

**追问**:
- "TIME_WAIT 状态的作用？" → 确保最后一个 ACK 到达，防止老连接干扰
- "UDP 需要握手吗？" → 不需要，无连接

**Q6: HTTP 和 HTTPS 的区别？HTTPS 的加密过程？**（3min）

**期望回答**:
| 特性 | HTTP | HTTPS |
|------|------|-------|
| 端口 | 80 | 443 |
| 加密 | 无 | SSL/TLS |
| 证书 | 不需要 | 需要 CA 证书 |
| SEO | 不利 | 有利 |

**HTTPS 加密过程**:
```
1. 客户端发送 Supported Cipher Suites
2. 服务端返回 Certificate（公钥）+ Selected Cipher Suite
3. 客户端生成 Pre-Master Secret，用公钥加密发送
4. 双方通过 Pre-Master Secret 协商出 Session Key
5. 后续通信使用 Session Key 对称加密
```

### 场景 2：消息队列选型

> 三个业务场景：
> 1. 用户行为日志（百万级 QPS，高吞吐）
> 2. 订单状态流转（强可靠，不能丢失）
> 3. 实时通知推送（低延迟，万级 QPS）

**问题**:
1. 分别推荐哪种 MQ？为什么？
2. 如果只能选一种，选哪个？
3. 如何保证消息顺序性？

**期望回答**:

| 场景 | 推荐 | 原因 |
|------|------|------|
| 日志采集 | **Kafka** | 高吞吐、顺序写、零拷贝 |
| 订单流转 | **RocketMQ** | 事务消息、高可靠 |
| 实时通知 | **RabbitMQ** | 低延迟、灵活路由 |

**只能选一个**: Kafka（吞吐量最好，可靠性也够）

**顺序性保证**:
- Kafka：同一 key → 同一 Partition
- RocketMQ：MessageQueueSelector
- RabbitMQ：单 Consumer 或 Queue 内有序

## 💡 面试官指南

### 基础问答评分标准

| 得分 | 标准 |
|------|------|
| 5 | 回答完整，能说出底层原理和细节 |
| 4 | 回答正确，能说出主要特点 |
| 3 | 回答基本正确，有部分遗漏 |
| 2 | 回答不完整，需要引导 |
| 1 | 基本不会，或完全错误 |

### 优秀候选人的特征
- ✅ 基础知识扎实，能说出原理而不仅是背诵
- ✅ 能快速理解场景，给出合理方案
- ✅ 能说出方案的优缺点和权衡
- ✅ 遇到不会的问题能坦诚承认并尝试推导
- ✅ 有学习新技术的热情和思路

### 需要警惕的信号
- ❌ 只会背诵八股，无法联系实际场景
- ❌ 设计方案不考虑边界条件和异常处理
- ❌ 对新技术毫无了解且不愿学习
- ❌ 逻辑混乱，无法清晰表达思路
- ❌ 遇到难题直接放弃

### 引导技巧
- 候选人卡住时："你可以先说说你的思路，不用急着写代码"
- 方案不完整时："如果流量再翻 10 倍，这个方案会怎样？"
- 没有考虑到某方面时："你觉得这个方案有什么风险？"
- 完全不会时："这个问题你可能没接触过，换个场景题试试？"
