## 第一部分：基础编程（10min）

### 题目 1：实现一个简单的 LRU Cache（必做）

**题目描述**:
```
设计并实现 LRU（最近最少使用）缓存数据结构。

要求：
- get(key): 如果 key 存在，返回 value，并标记为最近使用；否则返回 -1
- put(key, value): 插入或更新 key-value；如果超出容量，淘汰最久未使用的
- 时间复杂度：O(1)
```

**考察点**:
- 数据结构设计能力
- 边界条件处理
- 复杂度分析

**参考实现（Java）**:
```java
class LRUCache {
    private final int capacity;
    private final LinkedHashMap<Integer, Integer> cache;
    
    public LRUCache(int capacity) {
        this.capacity = capacity;
        this.cache = new LinkedHashMap<>(capacity, 0.75f, true) {
            @Override
            protected boolean removeEldestEntry(Map.Entry<Integer, Integer> eldest) {
                return size() > capacity;
            }
        };
    }
    
    public int get(int key) {
        return cache.getOrDefault(key, -1);
    }
    
    public void put(int key, int value) {
        cache.put(key, value);
    }
}
```

**追问**:
- "不用 LinkedHashMap 如何实现？" → 双向链表 + HashMap
- "如果要支持 LFU（最不常用），怎么改？" → 增加频率计数器

## 第二部分：场景分析（15min）

### 场景 1：电商大促场景

**背景**:
> 你是某电商平台的后端工程师。即将迎来 618 大促，预计流量是平时的 10 倍。老板要求系统不能崩，用户体验不能差。

**问题**:
1. 你会如何设计限流策略？
2. 如果数据库扛不住了，你会怎么做？
3. 如何保证下单流程的可靠性？

**期望回答方向**:

| 问题 | 考察点 | 参考方案 |
|------|--------|---------|
| 限流策略 | 是否了解常见限流算法 | 令牌桶/滑动窗口；Nginx 层 + 服务层多级限流 |
| 数据库压力 | 缓存使用经验 | 热点数据预热到 Redis；读写分离；分库分表 |
| 下单可靠性 | 分布式事务理解 | 本地消息表 / RocketMQ 事务消息 / Seata |

**加分项**:
- 提到"秒杀场景特殊处理"（隔离、降级、异步化）
- 提到"压测"（提前演练，发现瓶颈）
- 提到"熔断降级"（Sentinel/Hystrix）

### 场景 2：消息队列选型

**背景**:
> 公司要建设一个新的消息队列系统，有三个业务场景：
> 1. 用户行为日志采集（高吞吐，百万级 QPS）
> 2. 订单状态流转（强可靠性，不能丢失）
> 3. 实时通知推送（低延迟，万级 QPS）

**问题**:
1. 这三个场景分别推荐用哪种消息队列？为什么？
2. 如果只能用一种 MQ 满足所有场景，你会选哪个？
3. 如何保证消息顺序性？

**期望回答**:

| 场景 | 推荐 | 原因 |
|------|------|------|
| 日志采集 | Kafka | 高吞吐、顺序写磁盘、零拷贝 |
| 订单流转 | RocketMQ | 事务消息、高可靠、延迟队列 |
| 实时通知 | RabbitMQ | 低延迟、灵活路由 |

**如果只能选一个**:
- 选 Kafka：吞吐量和可靠性都能满足，只是延迟稍高
- 选 RocketMQ：可靠性最好，吞吐量也够

**顺序性保证**:
- Kafka：同一 key 发送到同一 Partition
- RocketMQ：SelectSentinel 或 MessageQueueSelector
- RabbitMQ：单 Consumer 或 Partition 内有序

**追问**:
- "消息积压了怎么办？" → 扩容 Consumer、临时增加 Topic Partition
- "如何保证消息不重复消费？" → 幂等性设计（唯一索引/分布式锁）

### 场景 3：分布式锁设计

**背景**:
> 你的系统需要在多台服务器上执行一个定时任务（比如每天凌晨统计昨日数据）。如何保证任务只在一个节点上执行？

**问题**:
1. 你会用什么方案实现分布式锁？
2. 如果持锁节点挂了怎么办？
3. 锁的粒度应该怎么设计？

**期望回答**:

| 方案 | 优缺点 |
|------|--------|
| Redis + SET NX | 性能好，但需要处理时钟回拨 |
| ZooKeeper | 强一致，但性能较差 |
| Redisson | 封装了 Redlock，推荐使用 |
| 数据库唯一索引 | 简单，但性能差 |

**持锁节点挂掉**:
- 设置过期时间（TTL）防死锁
- 看门狗机制自动续期（Redisson）
- 心跳检测 + 强制释放

**锁粒度**:
- 尽量细粒度（业务维度）
- 避免锁竞争（分片）

### 问题 3：Agent 的局限性

**问题**:
> 你认为当前的 Agent 系统有哪些局限性？在实际应用中会遇到什么问题？

**期望回答方向**:
- **幻觉问题**: LLM 可能生成错误信息
- **延迟问题**: 多步调用导致响应慢

- **可靠性问题**: 工具调用可能失败

**加分项**: 提到解决方案（如 Guardrails、缓存、 fallback 机制）

**需求**:
> 设计一个面向电商的智能客服 Agent，要求：

## 💡 面试官指南

### 优秀候选人的特征
- ✅ 能快速理解场景，给出合理方案
- ✅ 能说出方案的优缺点和权衡
- ✅ 遇到不会的问题能坦诚承认并尝试推导
- ✅ 有学习新技术的热情和思路
- ✅ 代码思路清晰，能边写边解释

### 需要警惕的信号
- ❌ 只会背诵八股，无法联系实际场景
- ❌ 设计方案不考虑边界条件和异常处理
- ❌ 对新技术毫无了解且不愿学习
- ❌ 代码逻辑混乱，无法表达思路
- ❌ 遇到难题直接放弃

### 引导技巧
- 候选人卡住时："你可以先说说你的思路，不用急着写代码"
- 方案不完整时："如果流量再翻 10 倍，这个方案会怎样？"
- 没有考虑到某方面时："你觉得这个方案有什么风险？"
- 完全不会时："这个问题你可能没接触过，换个场景题试试？"
